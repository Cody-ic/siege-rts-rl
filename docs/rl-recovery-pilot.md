## GPU 占用时的 CPU 方案

本轮发现 GPU 上有无关项目的任务，未修改其进程、优先级、显卡模式或资源配置。观察到计算模式为 Default、MIG 未启用；有 MPS 控制程序，但未发现运行中的服务。没有发现可用的 Slurm / PBS / LSF 命令；这只是当前账号可见范围内的结果，不代表管理员没有其他管理机制。

显存余量不等于算力余量，GPU 利用率表示采样时段内执行内核的时间比例，并不是可以直接分配的算力份额。MPS 的线程限制也不等于独占资源预留。参见 [NVIDIA 利用率定义](https://docs.nvidia.com/deploy/nvidia-smi/index.html) 与 [MPS 资源配置说明](https://docs.nvidia.com/deploy/mps/when-to-use-mps.html)。是否同卡共享应遵守服务器安排，不能通过终止别人的任务获得性能。

先测纯 CPU 是否足以做初筛，而不是把整个流程挂起：

| 设备 | 并行环境 | 仿真线程 / PyTorch 线程 | 两次更新步数 | 训练计时 | 吞吐 |
|---|---:|---:|---:|---:|---:|
| A800（先前空闲时） | 64 | 4 / 1 | 8,192 | 21.39 秒 | 383 env-step/s |
| CPU（本轮） | 64 | 4 / 4 | 8,192 | 34.21 秒 | 239 env-step/s |

均为近距离课程开头的短测，不含进程启动与初始建局；运行时刻、机器负载和 PyTorch 线程配置不同，不能当作严格的硬件对照或全程耗时预测。CPU 方案足以先做有限预算筛选。CPU 训练必须设置 `CUDA_VISIBLE_DEVICES=`，避免 CUDA 版 PyTorch 的随机状态保存等辅助路径意外占用 GPU。

## 三组短训

按每组累计 200,000 env-step、64 个环境、4 个仿真线程、4 个 PyTorch 线程串行执行。分组仍是 economic + 真实守方、victory + 真实守方、economic + 空城；胜利奖励均为 2000。每组使用独立目录，每次更新保存，阶段结束再冻结评估。实际步数可向上取整不到一个环境批次。

“空城对照”是项目原有分组名称，具体开关是关闭脚本守方，建局仍使用同一地图与数值表，不代表移除地图上的建筑。该组的评估也关闭脚本守方，不能把它的胜率直接当作对抗真实守方的胜率。

本次三组是从同一训练种子新建的对照，不把旧模型热启动混入其中；旧权重仍保留，可另建同预算热启动实验。三组训练均完成 200,000 env-step，共 600,000 步；每组结束时完成 448 局，训练期间均未出现胜局。课程均从 `frac=0.15` 推进到 `frac=0.3`，尚未到实际集结点。

| 分组 | 实际训练步数 | 最终课程距离 | 训练期间胜局 / 完成局 | 累计训练吞吐 |
|---|---:|---:|---:|---:|
| economic + 真实守方 | 200,000 | 0.3 | 0/448 | 205.30 env-step/s |
| victory + 真实守方 | 200,000 | 0.3 | 0/448 | 205.32 env-step/s |
| economic + 空城对照 | 200,000 | 0.3 | 0/448 | 275.25 env-step/s |

这些训练局混合了持续更新的策略和不同课程距离，不能作为固定策略胜率，也不能与旧模型的冻结评估直接比较。吞吐是各组训练计时内的累计值，不含后续冻结评估和整个驱动流程开销。

单项 0/32 胜的 Wilson 95% 区间仍为约 0%–10.7%。新模型的近距离为 `frac=0.3`，旧模型表格为 `frac=0.15`，不能横向当作同一难度；只有实际距离 `frac=1` 一致。空城组缺少脚本守方，其伤害也不能直接用来判定它优于另外两组。

两组真实守方新模型在实际距离均有 8 局接触建筑，旧模型在同一评估条件下均为 0 局。这是值得跟进的行为信号，但训练预算、历史版本和初始化不同，且只有一个训练种子，**不能据此声称新训练方案已胜出**。胜利奖励组的实际距离伤害较高，也不足以据此确定最终奖励方案。

### 下一阶段优先级

1. 先按进攻入口拆分轨迹、动作分布、流场方向与第一次建筑接触时间，解释剩余 24/32 局为什么没有接触建筑；分别检查冻结最大概率动作和按概率采样，避免把执行方式的差异误判为完全没有学到。
2. 针对定位出的推进问题，在独立实验中验证导航辅助或更平缓的课程距离变化。若使用规则示范或辅助损失，要显式记录并另设对照，保留现有 RL 观测、合法动作与自主决策接口。
3. 对旧 victory 权重热启动与从零训练做同预算对照，保留规则 flow 基线；确认稳定推进后再增加训练种子和地图，使用新的最终测试种子验证。旧权重不覆盖，新规则和奖励变更不混入原运行目录。
