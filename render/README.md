# render — 正式前端

**不是调试视图。** `CLAUDE.md` 明写「`render/` 不是『调试视图』，而是正式前端，
工作量要按正式前端估，**预算 5–8 人日**，不要按『画几个方块』来排期」。
它同时兼任 RL 调试工具——调策略时必须能看观测张量、奖励信号与目标选择。

> 设计决策不在本文。契约在 `CLAUDE.md` 与 `地图与场景设计.md`，
> 本文只写「怎么跑」与「分了几期」。

## 怎么跑

`render/` **默认不参与构建**（不变量 2、3 的构建侧落地），要显式打开：

```bash
cmake -B build -DRTS_BUILD_RENDER=ON
cmake --build build --config Release

# 窗口模式
./build/render/Release/rts_render.exe \
    --map game/testdata/fixture_min.json \
    --sprites tools/sprite_gen/out_3d

# 截图模式：渲一帧导出成 PNG 后退出，不开窗口
./build/render/Release/rts_render.exe \
    --map game/testdata/fixture_min.json \
    --sprites tools/sprite_gen/out_3d \
    --screenshot out.png --size 1200 700

# 素材校验：把元数据声明的每一张精灵都载入一遍。不需要 --map
./build/render/Release/rts_render.exe \
    --verify-assets --sprites tools/sprite_gen/out_3d
```

窗口模式下：方向键 / WASD 平移，滚轮缩放（以鼠标为锚），中键拖拽，`F` 重新入画。
光标所在格会高亮，旁边显示这一格上有什么（地形、墙段残血、资源点、集结点、禁建）。

**首次配置要下 42 MB 的 raylib 源码包。** 已有本地副本时可以完全不走网络：

```bash
cmake -B build -DRTS_BUILD_RENDER=ON -DFETCHCONTENT_SOURCE_DIR_RAYLIB=<路径>
```

### 截图模式为什么存在

不是为了省事，是为了**让渲染结果不必靠人盯着看才能验**：

- 评审能跑一遍、对着 PNG 看，不必自己开窗
- 有回归测试可挂（`ctest -R render_smoke`）
- `#16` 的「双视图」（真实战场 vs AI 以为的战场）本来就要离屏渲染，是同一套手法

它用 `RenderTexture` 而不是 `TakeScreenshot`：**隐藏窗口的默认帧缓冲在 Windows 上
读回来是黑的**（实测），而离屏纹理不依赖窗口可见性。

### `--verify-assets` 补的是哪块空白

在它之前，「元数据声明了某个状态、但 PNG 没渲出来」**没有任何检查覆盖**：

- `tools/sprite_gen/check_assets.py` 查的是 `assets.json`——模型路径存在、
  主体模型没被两个实体共用。它不看渲染产物
- `SpriteAtlas::preload_idle()` 只覆盖 `idle` 四朝向

于是那类错最早暴露的时机是**动画第一次播到那个状态**，也就是实体渲染做完之后。
`#41` 把素材从 300 张扩到 476 张、状态从 `idle`/`move` 扩到含 `attack`/`work`
之后，这块地带就不再是可以不管的了。

**它与 `check_assets.py` 互补而非重复**，因为它跑的是**读取器这一侧**的文件名规则
（`SpriteAtlas::file_name()`）。生成器侧或读取器侧各自的检查都抓不到
「两侧约定漂移」，而换素材包时那正是最容易发生的事——两边都自认为对。

两条 ctest：`render_verify_assets`（真素材必须全绿）与
`render_verify_assets_missing_is_red`（`WILL_FAIL`，夹具声明了两张精灵、
目录里零 PNG）。后者的夹具刻意带**真的** `px_per_tile` / `tile`，
为的是走到「载入 PNG」这一步才失败——否则它会因为「元数据格式不对」而红，
看着一样绿，实际没验到想验的那一步。

## 分层

```
SpriteAtlas      读 _sprite_meta.json + 按需载入 PNG，给出 (纹理, 地面锚点)
FontSet          载入中文字体，并把「渲错」的三种方式全部变成会抛的错
SceneRenderer    两遍绘制：先整片铺地砖，再按深度键画叠加物与实体
SceneOverlay     场景内 UI：格高亮（世界空间）+ 光标旁的信息条（屏幕空间）
CameraController 平移 / 缩放 / 让整张地图入画
```

**那些该被测的规则不在这里**，在 `game/`：地形展开、变体挑选、走向推导、深度排序、
**等距投影正反两向**（`game::IsoProjection`）、**中文展示名与格描述**
（`game::display_names`）。理由是 `render/` 默认不配置，挂在它下面的测试在默认构建里
根本不存在、ctest 照样全绿，而这些正是「只值一行代码但错了才发现」的那种。
见 `game/CMakeLists.txt` 开头。

于是 `render/` 只剩「拿绘制列表去 blit」，而它拿到的绘制列表里**没有可变的仿真状态**
——不变量 2 因此是类型层面的保证，不是约定。

### `IsoProjection` 为什么在 `game/`

它上一版在这里，是放错了——按上面那条准则，**投影数学必须在默认构建里被测**。
反方向（`screen_to_grid`，屏幕像素 → 格坐标）尤其：用 `floor` 代替 `round`
会让点选**稳定偏半格**，而那看起来像美术锚点没对齐，改精灵怎么改都不对。

这不违反 §7「像素几何只有一个来源」：`IsoProjection` 不含任何像素数字，
`px_per_tile` 由构造参数注入，来源仍是 `_sprite_meta.json`（经 `SpriteAtlas`）。

附带得到一条对齐保证：`round` 的原像正好是 `|dx|/(tw/2) + |dy|/(th/2) ≤ 1`，
也就是**格高亮画出来的那个菱形**。所以「看见高亮的那格」与「点下去选中的那格」
在数学上是同一个区域，不是调出来的。已用像素核对过（134×69 @ (599.5, 484.0)
对解析值 134.4×67.2 + 1.6 线宽 @ (600.0, 484.4)）。

## 已知限制与分期

### 现在能做什么

读一张地图文件、画出地形与初始墙段、平移缩放、查看光标所在格、中文界面文字。
**没有实体渲染**（等 `rts_core` 接口）。

### 中文文字：三个坑，三道检查

**中文渲错的三种方式全都不会自己报错**，所以 `FontSet` 存在的理由不是「载入字体」
这件事难，而是这三种失败都长得像正常工作。三条都是实测出来的：

| 坑 | 表现 | 检出 |
|---|---|---|
| 码点在集合里、字体没那个字 | **零宽的什么都没有**（连豆腐块都没有） | 构造期：逐码点核位图 |
| 字体有那个字、码点没进集合 | 渲成 `?`；集合不含 ASCII 时渲成图集第一个字形——实测「镇野箭楼」渲成「平平平平」 | `draw()` 逐码点核集合成员 |
| 传了 `.ttc`（字体集合） | raylib **静默退回内置字体**，且 `texture.id != 0`，看不出失败 | 构造期：字形数必须正好等于要的个数 |

第二个最坏：四个看着完全合理的汉字，肉眼都不一定看得出来。由此推出本目录唯一一条
对上层的硬要求：

> **码点集合必须由「我们真的要显示哪些字」机械推导，不能手抄一个 Unicode 区间。**

输入是 `game::all_display_strings()`（枚举展示名按 count 遍历得出）+
`render::ui_strings()`（界面字面量）+ **地图文件里的 `name` / `map_id`**。
最后一项容易漏——它是来自数据的任意中文，不在任何清单上。将来单位属性表从 JSON
读进来时同一条约束照样成立：**任何要显示的数据串，都必须在建字体之前登记。**

还有一条边界值得记：全角空格 U+3000 在 simhei 下**宽度为 0**，用它当分隔符各项会
糊成一片，而空白类字符本来就被免掉了位图检查——所以那条豁免收紧成「可以没有墨，
但不能没有宽度」，分隔符改用 ASCII 空格。

顺带发现一处与本目录无关但影响全项目的事：**MSVC 的 C4062（switch 漏枚举值）是
off-by-default，而 GCC 的 `-Wswitch` 含在 `-Wall` 里**。已在
`cmake/CompilerWarnings.cmake` 显式开上 `/w14062`，理由与实测记在那里。

#### 字体来自系统，不随包分发（这条要小组知道）

候选是 `C:/Windows/Fonts/simhei.ttf`、`Deng.ttf`，两个都实测通过；`--font` 可覆盖。
**只放纯 TTF**——Windows 上的 `msyh.ttc` / `simsun.ttc` 与 Linux 上常见的 Noto CJK、
文泉驿都是 `.ttc`，全都会触发第 3 个坑。

用系统字体换来的是：不往仓库里塞十几 MB 二进制、不多一个 FetchContent、
任何 Windows 上都能跑。**代价是交付包有一条未声明的依赖。** 若小组认为交付包必须
自带字体，替代方案是「取一份 OFL 字体 + 用 fonttools 按码点集合子集化」——
子集化之后大约一两百 KB，可以入库，而码点集合本来就是机械推导出来的，现成可用。
这一步现在不做，是因为它属于打包方式，而 `交付要求的工程影响.md` 把打包留到第 3 周。

**这条与「命名纪律」是一致的**：代码标识符一律英文，中文只在展示层——
`game::display_names` 就是那个展示层的唯一入口，别在别处再翻一份。

#### ImGui 为什么从 PR C 挪到了 PR E

原先的排期把 ImGui 排在 PR C，并写着「此时仍无实体数据，面板先接假数据」。
**那句话本身就是这个仓库一直在防的那种做法**：硬编码的数字在界面上和真数据长得
一模一样，于是「这个面板到底接没接上」变成一个要读代码才能回答的问题。

而 ImGui 的价值全在它能显示什么。现在没有仿真数据，一个 ImGui 面板能显示的东西
不会超过 `draw_hud()` 那三行已经显示的（地图、尺寸、地砖数、深度序列长度），
只是换了个更漂亮的框。**真数据到位之后再引它，那时它一次就能做对。**

反过来，中文字体与反向投影不能等：前者是「界面能不能说中文」，
后者是点选与建造放置的前置，两者都与 `rts_core` 接口无关，且都已经能被测。

### PR F 的由来与它缺的那一条

`#41` 给攻击态补了精灵，但同时发现 **`Tower` / `Flak` / `Ram` 是静态网格、零动作**，
而且这不是缺陷：

> `Tower` 是齐射覆盖、`Flak` 是单体狙击——这两者作为**弹道**天差地别（一片箭雨 vs
> 一条曳光），作为**塔身动画**则毫无区别。

所以「它在开火」这件事在 256 px/瓦片的尺度下只能靠**飞出去的那一发**表达，
而那是运行时绘制、不是精灵流水线。这条正好接上 CLAUDE.md「机制信息由视觉剪影与 UI
承担」——塔身动画传达不了机制差异，弹道能。

**它缺一条接口上的信息**：要画一发箭从 A 飞到 B，前端得知道「这次攻击的目标是谁 /
哪一格」。`Ram` 那条更明确——CLAUDE.md 写它「弹道有飞行时间」，那**飞行时间是仿真的
一部分**（AOE 落点与散开的单位有关），不是纯视觉。因此「在途弹丸」要不要进观测与回放，
是接口那一层要答的，已提到 `rts_core` 那边。

### 动画状态机的一条硬要求（来自 #41）

攻击态的元数据带 `impact_frame`（打出去的那一帧）。**正确用法不是按固定节奏播完**，
而是「保持命中前的帧，直到仿真说前摇结束，再播其余帧」——攻击前摇是**待标定数值**，
按帧数决定时长等于把一个待定数值烤进资产里。

`SpriteAtlas::impact_frame_of()` 已经把这个字段读出来了，并校验它真在 `frames` 里
（不在就构造时抛：症状会是「动画停在不存在的帧上等前摇结束」= 单位看着卡住，
像仿真 bug 而根因在资产）。
