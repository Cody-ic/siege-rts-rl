# 精灵生成

两条产图路线，产物格式相同（`<标识符>_<状态>_<朝向>[_<帧号>].png`），前端代码不因换图而改动。

| 路线 | 脚本 | 用途 |
|---|---|---|
| **程序化占位** | `gen.py` | 第 1 周立刻可用，不依赖任何素材。尺寸与投影角必然一致 |
| **场景预览** | `preview_map.py` | 拼一张等距场景，兼作前端贴图与深度排序的参考实现 |
| **真实素材** | `blender_render.py` + `postprocess.py` | 正式画面。CC0 模型经统一相机与灯光预渲染成等距精灵 |

## 路线一：程序化占位

```bash
python gen.py out
```

输出 `out/<标识符>_<朝向>.png` 与 `out/_contact_sheet.png`。无依赖（仅 Pillow），
用于在美术就位前解锁前端开发。

## 路线二：真实素材

### 1. 只用 CC0 素材

**这是硬性要求，不是偏好。** 交付清单要求提交「软件源代码，包括输入文件」，
素材需随仓库提交。CC0 允许无条件复制、修改、再分发；其他"免费"许可通常不允许。

已核实可用的来源：

| 来源 | 许可 | 覆盖 |
|---|---|---|
| [Quaternius](https://quaternius.com/) | CC0 | knight、monsters、Animated Animal Pack（含 **Horse**）、Fantasy Props |
| [KayKit](https://kaylousberg.itch.io/) | CC0 | **Skeletons**、Adventurers、**Medieval Builder**、Dungeon |
| [Kenney](https://kenney.nl) | CC0 | 地形、瓦片、建筑 |
| [Poly Pizza](https://poly.pizza/) | **混杂** | 聚合站，含大量 CC-BY 的 Google Poly 存档，**须逐个查看许可标签** |

**不要使用 [Reiner's Tilesets](https://www.reinerstilesets.de/graphics/lizenz/)**：
其许可禁止将原始素材（含修改版）上传到自己的页面，与本项目"素材入库并随源码交付"冲突。

### 素材包本身的坑（下次换素材大概率还会撞上）

| 症状 | 原因 | 应对 |
|---|---|---|
| 模型整体渲成**品红** | `.blend` 把纹理路径写成与自身同级，分发时纹理却在单独的 `Textures/` 目录 | `relocate_missing_textures()` 按文件名逐级向上搜索并改写 `filepath`。Blender 的 `file.find_missing_files` 算子在无头模式下不可靠 |
| 渲出**空图** | 网格被作者设了 `hide_render=True`（Quaternius 的 Skeleton 即如此） | `normalize()` 中强制 `hide_render = hide_viewport = False` |
| 模型停在**默认姿态**（鹰只剩两片下垂的翅膀） | `libraries.load` 会载入动作数据块，但不会绑到骨架 | `set_action()` 显式指定；动作名各包不同（`Idle` / `Skeleton_Idle` / `Bat_Flying`），找不到时会打印可用列表 |
| 跨包组合比例失调 | 各包尺度互不相干（马高 6.91、骷髅高 5.09，原始单位无可比性） | `parts` 的 `scale` 先对齐比例，再用 `offset` 定位 |
| 拼装时**某个部件静默停在默认姿态** | 多包动作重名（马与盗贼都有 `Idle`），后载入的被 Blender 改成 `Idle.001`；按全局名查找会把马的动作绑到骑手骨架上，骨骼名对不上则**不报错** | `set_action()` 的候选限定在该部件刚载入的动作里 |
| 染色调到能看出阵营时，模型**糊成一块平色** | 线性混合按比例抹掉纹理明暗 | 默认改用 `COLOR` 混合：只换色相饱和度、明度照抄原图 |
| 想要冷色却染出**暗红** | `MULTIPLY` 只能压暗，加不出原图没有的颜色（棕马乘幽紫 = 暗红） | 幽灵战马那类须两步：`COLOR` 换色相 + `brightness` 压暗 |
| 染色与提亮**双双无效**，模型始终一团黑 | 该模型的本色明度极低（鹰的翅膀只有 0.04），`COLOR` 照抄明度就还是黑的；而 `brightness>1` 走混色节点时被颜色输入钳制到 1，等于没乘 | 这类模型改用 `tint_mode: "MIX"` 直接换色；提亮已改走不钳制的向量缩放节点 |
| 武器待机帧在手上、**一跑就脱手** | 按世界坐标摆放的绑定是静态的，手臂一动它留在原地 | `attach` 建立真正的骨骼父子关系 |

另外两个已知坑：Quaternius 的 **FBX 动画会损坏**，请用 `.blend` 或 glTF；
KayKit 的 **Legacy 版本**风格陈旧，须取重做后的新版。

### 2. 放置模型并登记

模型放在 `models/<素材包>/`（**保留素材包原目录结构**，否则 `.blend` 引用的纹理会失效），
然后在 `assets.json` 中登记。各家模型的朝向、尺度、原点、动作名都不一致，
这些差异**全部在 JSON 里用数据抹平**，不改脚本。

登记项：`cn` 中文名、`yaw` 朝向校正、`height` / `max_width` 尺寸、`lift` 抬升（空中单位）、
`action` / `frames` 动作与帧、`tint` / `tint_mode` / `brightness` 阵营染色。字段含义见
`assets.json` 顶部的 `_comment`。

**模块化素材用 `parts` 拼装**：Kenney 城堡包的塔身分为底座/中段/顶层/屋顶数块，
每块都从 z=0 起建模，单独渲染只是塔的一截。`parts` 按累计高度自下而上堆叠，
`gap` 可微调各段间距（旗帜等装饰件常需负值下沉）。

`parts` 同样用于**跨素材包组合**：鬼域骑士团 = 幽灵战马 + 骷髅骑手 + 压平的骑枪。
此时用 `scale` 对齐比例、`offset` 显式定位（设了 offset 即不参与堆叠）、`rot` 调整
握持角度（武器模型原点都在握把处，绕原点旋转正好等于改变持握姿态）。

### 骑乘：`pose` 与 `attach`

素材包里**没有骑乘动作**，直接把骑手放上马背，双腿会整根插进马腹。`pose` 在动作之上
叠加手工骨骼角度，把大腿前摆外张、小腿回折，绕开马身：

```json
"pose": { "L.UpperLeg": [70, 0, 35], "L.DownLeg": [-60, 0, 0] }
```

绕**局部 X 轴是前后摆动**，局部 Y 是骨骼自身轴向、转了没有任何效果（骨骼的局部 Y
就是骨长方向）。角度靠单独渲一次骨架标定即可，不必凭空猜。

`pose` 会**先在该帧求值再清除动作**——动作每次换帧都会重写骨骼变换，不清除的话手工
角度会被动画系统悄悄冲掉。副作用是该部件从此定格，所以马能跑而骑手保持坐姿。

武器用 `attach` 绑到骨骼上，不要按世界坐标估位置：

```json
{ "model": ".../Warrior_Sword.blend", "attach": "R.DownLeg.001", "rot": [-90, 0, 0] }
```

`attach` 建立的是**真正的骨骼父子关系**，不是算一次世界矩阵摆上去。这个区别只在
动画里才暴露：摆放式绑定在定格的部件上看着没问题，但骷髅一跑起来手臂摆动，
静止摆放的剑就留在原地脱手了——而**单看待机帧完全正常**。

原点是**骨尾**（即手部），局部 Y 沿骨长，所以手持武器的 `offset` 通常就是 0。
清单里的 `scale` 是世界尺度，代码会除掉从骨架继承的那一份缩放，与非绑定部件同义。

调握持角时注意：**等距视角下指向镜头的武器会被压缩成一条细缝**，看着像"尺寸变小了"。
判断尺寸对不对要看待机帧，不要拿奔跑帧下结论。

两个已知的命名坑：Quaternius 的**骷髅没有手臂骨骼**——它把手臂也命名成了
`*.UpperLeg.001`（肩高 z=3.23，从名字完全看不出来）；q_rpg 的人形角色则带一根
现成的 `Weapon.R`，武器直接绑上去即可。

### 动画状态

每个实体用 `states` 声明若干状态。**状态名不是固定集合**，按实体的机制来定：

| 状态 | 谁有 |
|---|---|
| `idle` | 全部实体（未声明 `states` 的建筑也算有一个） |
| `move` | 会移动的单位 |
| `attack` | **会攻击**的实体：`Spear` / `Archer` / `Ranger` / `Ghoul` / `Knight` / `Shade` / `Ram` / `Phoenix` / `Flak` / `Tower` |
| `work` | `Mason`。它**无战力**，叫 `attack` 是错的——同一套动作在机制上是维修 |

**能攻击的实体现在全都有 `attack` 了。** `Tower` 是最后一个补上的（2026-08-30）：
它全部由单网格塔块堆成、**没有可动部件**，所以攻击表现不由塔身承担，而是
**垛口上待发的那支箭**（`only_meshes` + `mesh_anim` 控可见性，见 §2.2）。
`Scout` / `Wraith` 零战力，不需要。

> **这一段此前写着「唯一还没有 `attack` 的是 `Tower`」，而它是第三处。**
> 补 `Tower` 时改了 §2 那张表与新写的 §2.2，**漏了这里**——同一件事写在三处，
> 改动时只想起了正在编辑的两处。这与 §8.3 记的「四朝向名单写在三处」是同一个形态，
> 也正是本仓库反复吃亏的那条：**同一件事写在多处然后漂移。**

```json
"states": {
  "idle":   { "action": "Idle_Weapon",  "frames": [1] },
  "move":   { "action": "Run_Weapon",   "frames": [1, 6, 11, 16] },
  "attack": { "action": "Sword_Attack", "frames": [1, 7, 13, 19], "impact_frame": 13 }
}
```

动作挂在 `parts` 里的实体（骷髅、骑兵）改用 `parts` 覆写，键是部件下标：

```json
"move": { "frames": [1,6,11,16], "parts": { "0": { "action": "Run" } } }
```

未声明 `states` 的实体（建筑、攻城锤）视为只有一个 `idle` 状态，前端因此可以
对所有实体一视同仁地按 (标识符, 状态) 取图。

带武器的角色要用 `*_Weapon` / `*_Holding` 动作变体（`Run_Weapon`、`Run_Holding`），
否则奔跑时武器会脱手——这类模型的武器是**模型自带**的，与 `attach` 无关。

**画布按全部帧的并集确定**，否则奔跑循环里前后腿全展的那几帧会被悄悄裁掉。

### `impact_frame`：**精灵资产不得编码任何待定数值**

`CLAUDE.md` 有「弓手有攻击前摇与转身速度，被贴脸即废」这条机制，而**前摇时长是待标定
的数值**。若前端按「N 帧匀速播完」来放攻击动画，那么改前摇就得重渲精灵——
一个待定数值被烤进了资产里。

所以攻击态额外给一个 `impact_frame`：本状态里**打出去**的那一帧（弓弦松开 / 刀锋落下）。
前端的正确用法是

> **保持命中前的帧**直到仿真说前摇结束，再播其余帧。

于是帧数与 tick 解耦，精灵只提供**关键姿态**、不提供**时长**。
这条与 `地图与场景设计.md` 6.3「回放格式不得依赖待定数值」是同一条原则的资产版。

命中帧要挑在**刀锋落下 / 箭离弦**那一帧，不是挥起的顶点——第一版就标错了两个
（`Spear` 标在举刀最高处、`Ghoul` 标在骨剑过顶处，两者都还差一整个下劈）。

### `pose_frame`：骑兵的攻击态需要它

`pose` 会**先在某帧求值再清除动作**（见下节），所以骑手是定格的。默认求值帧是
`frames[0]`，而 `frames` 同时还在驱动**马**的步态——两者绑在一起的话，
要让骑手停在挥击帧就得把马的步态也从那一帧起采，攻击态与移动态的马腿相位就不同了，
看着像卡了一下。`pose_frame` 把两者分开。

注意 `libraries.load` 只拉 `objects` 时，**仅有当前绑在对象上的动作会跟着进来**
（马的 `Run` 就因此缺失），所以要显式载入 `actions`。

### 阵营配色

**染色的职责是让玩家一眼分清敌我**，不是美化。守方戍卫弓手与攻方亡灵弓手曾共用同一个
模型、只靠染色区分——这在剪影上完全读不出阵营，属于机制可读性缺陷（见 CLAUDE.md
「风味名不得遮蔽机制可读性」）。现在攻方一律为骷髅形体 + 幽蓝/幽紫冷色，守方为
有血肉的人形 + 自然暖色；同为骑兵的逐风猎骑与鬼域骑士团靠**活马 vs 幽灵马**区分。

三个模式各有其不可替代之处，选错了只能靠加大强度硬凑，结果是把模型抹平：

| 模式 | 行为 | 用在哪 |
|---|---|---|
| `COLOR`（默认） | 取染色的色相饱和度，**保留原纹理明度** | 绝大多数情况。要"更明显"应加大饱和度，而非强度 |
| `MULTIPLY` | 只能压暗，**加不出原图没有的颜色** | 压暗金属、木料 |
| `MIX` | 线性混到平色，会抹掉明暗层次 | 基本不用 |

`brightness` 补上 `COLOR` 做不到的明暗调整：幽灵战马是「换色相 + 压暗 0.55」，
空中单位则要**提亮**（蝙蝠贴图本身很暗，不提亮在地表上根本看不见）。

### 3. 渲染

```bash
blender --background --python blender_render.py -- --manifest assets.json --out out_3d
blender --background --python blender_render.py -- --only Knight,Phoenix   # 只渲部分
python postprocess.py out_3d
```

## 尺寸约定：一律以**格子边长**为 1

`TILE_SIDE = 1/√2 ≈ 0.707` 世界单位。约定是「1 世界单位 = `px_per_tile` 像素
（沿屏幕横轴）」，而边长 s 的正方形投影后横跨 √2·s，故 s 取 1/√2 才能让菱形正好是
`px_per_tile × px_per_tile/2` 像素。**改这个数等于改掉整套素材。**

`height` / `max_width` / `lift` 都以**格边长**为 1，`max_width = 1.0` 正好占满一格。
早先误以菱形的**屏幕宽度**为 1，等于把所有实体放大了 √2 倍——单位比地砖还大、
大树比战马还矮。这类比例错误在单看一张图时完全看不出来，**必须把不同类实体
按锚点对齐排在一起才会暴露**。

### 三种定标方式

| 方式 | 行为 | 用在哪 |
|---|---|---|
| `modules: k` | 1 个模型单位 = k 格边长，**不做归一化** | Kenney 全套 |
| `kind: "tile"` | 按水平 footprint 定标到一格 | 地砖 |
| `height`（默认） | 按高度定标，`max_width` 约束水平尺寸 | Quaternius 角色 |

**Kenney 整套件都建在 1.0 模数上且内部自洽**（墙高 1.31、塔身 1.01、大树 1.85、
攻城锤长 2.09、地砖 1.00），所以统一乘一个系数即可让全套件与格子、以及彼此之间的
比例自动正确。**逐个手调高度反而会破坏这份自洽**——这是上一版比例失控的直接原因。

Quaternius 的角色原始尺度毫无可比性（马高 6.91、骷髅 5.09），只能按高度归一化。
步兵定为 0.9 格边长，骑兵 1.2。

## 地形三类：地面 / 障碍物 / 资源点

`kind: "tile"` 的条目是地砖：画布不留白、菱形正好占满，后处理跳过描边与投影
（地砖本身就是地面，描边会让整片地面变成一张黑格子网）。

**地形标识符必须与 `地图与场景设计.md` 4.1 的枚举一致**——那份文档是地图格式契约，
`rts_core` / `render/` / `train/` / `tools/` 四个模块都吃它。当前枚举五种：

| 精灵 | 枚举 | passable | blocks_vision |
|---|---|:-:|:-:|
| `Plain` + `PlainB` / `PlainDirt` / `PlainRoad` / `PlainAsh` | `Plain` | ✓ | ✗ |
| `Rock` | `Rock` | ✗ | ✓ |
| `Forest` | `Forest` | ✓ | ✓ |
| `Water` | `Water` | ✗ | ✗ |
| `Bridge` | `Bridge` | ✓ | ✗ |

`Plain*` 四个只是**同一枚举值的贴图变体，不占枚举位**——渲染层按坐标哈希选变体，
不写进地图文件。`PlainRoad` 是纯美术路面：契约否掉的是 `Road` 的**加速效果**，
不是路面贴图，仿真里它仍是 `Plain`，因此不会诱导路径收敛。

**障碍物不是装饰。** CLAUDE.md 的「骑兵冲锋助跑距离」「集结点方向选择」
「视野遮挡是侦查的物理基础」「flow field 寻路」四条都以它们为前提。
`Water` 填的是通行 × 视野四种组合里唯一空缺的那格（挡路不挡视野），
带来岩壁给不了的质感：看得见对岸集结却打不着。

## 三个视觉族，区分必须靠**剪影**而不是配饰

玩家在游戏节奏下读的是剪影。因此登记新条目时先确认它属于哪一族：

| 族 | 成员 | 剪影特征 | 机制 |
|---|---|---|---|
| **人造建筑** | `Quarry` / `Lumber` / `Mine` | **三个互不相同的形体** + 资源色横幅 | 我的经济建筑，必须守 |
| **砌体战斗塔** | `Tower` / `Flak` | **实心塔身 + 尖锥顶**，或顶部器械；中段是**射孔窗** | 石材造，**有火力** |
| **房屋** | `Barrack` | **拱门 + 阁楼窗坡顶**，只有战斗塔一半高 | 石+木，**零战力**，人从这里进出 |
| **木构辅助建筑** | `Watch` / `Lumber` / `Fence` | **镂空骨架，透光、看得见背景** | 木材造，零战力或经济 |
| **可破坏障碍** | `Stump` / `Rubble` / `Sapling` | **矮而单薄**，单件 | 有血量，能被打穿开路 |
| **不可破坏障碍** | `Rock` / `Forest` / `ForestB` | **高而厚重**，多件或粗壮 | 永久，防线可以依靠它 |

三座资源建筑分别是**石拱吊架 / 开放木构棚架 / 尖顶井口房**——刻意不共用主体构件。

「砌体战斗塔」与「木构辅助建筑」的界线是**实心 vs 镂空**，不是颜色。它承载一条机制区分：
`Watch` 与 `Tower` 争同一个位置，构成「看得见 vs 打得着」的取舍（CLAUDE.md 建筑花名册），
玩家必须在游戏节奏下认出哪座放弃了火力。族内再靠**高矮**分：
`Watch` 2.94 三节高瘦、`Lumber` 1.15 矮方、`Fence` 贴地。

### `Barrack` 原先挂在「砌体战斗塔」那一族，那是错的

上表那一行曾写成 `Tower` / `Flak`**（+`Barrack`）**——**那个括号就是心里有数但没解决的痕迹**：
族的定义是「石材造、**有火力**」，而 `Barrack` 零战力（它是部队产出点）。

构件上它当时是 `square-base` + `square-roof` 两件，于是剪影读作**「矮一点的战斗塔」**，
而族内区分靠的正是高矮——**用族内维度去承担跨族差异**。评审直接指出「太像」。

**这与 `Watch` 那次是同一个错误的第二次出现**：那次是拿染色深浅去表达材质
（修法见下面第 7 条），这次是拿高矮去表达有没有火力。共同形态：
**用程度性差异（深浅 / 高矮）去表达类别性差异（材质 / 有无火力）。**

修法因此不是「把它做得更矮一点」，而是让差异铺在三个维度上、其中两个是**类别性**的：

| | `Tower` | `Barrack` |
|---|---|---|
| 中段 | 射孔窗 ×2 | **拱门**（`tower-square-mid-door`） |
| 顶 | 纯尖锥 + 垛口层 | **坡顶 + 阁楼窗**（`tower-square-top-roof-high-windows`） |
| 高度 | 4 段 | **2 段**，约一半 |

前两条是有/无，第三条才是程度——**顺序很重要**：只有第三条的那一版就是被指出「太像」的那一版。

门是「这里出兵」最直接的语言；阁楼窗是「里面住人」。CLAUDE.md 写 `Barrack` 是
「石+木」，两者都对得上。**它现在一件构件都不与人共用**，所以 `check_assets.py` 的
`ALLOW_SHARED` 里不再给它留位置——留一条用不到的豁免比没有更坏，
它会在将来真的共用时静默放行。

#### 淘汰过两个候选，第二个是踩进了本文件自己记的坑

**`tower-square-arch`（拱券）**：双开口，剪影读作门廊或凉亭，而且会与 `Gate` 混——
`Gate` 是城墙上的既定薄弱点，认错它的代价比认错兵营大。

**`tower-slant-roof`**：看名字以为是斜屋顶构件，**渲出来发现它是一整座小屋**，
而 `Mine`（尖顶井口房）的主体正是它。于是改完变成「`Barrack` 与 `Mine` 是同一座小屋、
只差颜色和垫高」——**刚修掉的形态原样重现，只是换了个对手**。

这一步本该避开：8-28 的日志里就写着「**先渲一张构件对照表再设计，不要照文件名猜**
（`tower-slant-roof` 不是屋顶构件而是一整座小屋）」——**同一个文件、同一句话、
连举的例子都一样**。教训不是「要小心」，而是：

> **`check_assets.py` 查不到这一类。** 它只查**主体**（`parts[0]`）共用，而
> `slant-roof` 在 `Barrack` 里是配件、在 `Mine` 里是主体，所以检查是绿的、
> 图是像的。**「共用」的视觉后果与它在 `parts` 里的下标无关。**

（现在这版不共用任何构件，所以那个缺口没被触发。要不要把检查扩到配件，
取决于愿不愿意接受一批合理共用的噪声——`flag-wide` 就被四座建筑共用。暂不改。）

**可破坏障碍在 `assets.json` 里是独立的 `obstacles` 分组，不在 `terrain` 里。**
理由是机制：地形是静态枚举、载入时展开成三张位图，**没有血量**；
可破坏障碍有血量，必须进实体扁平数组。把它们放在 `terrain` 分组下，
就是「文件结构与文件说明互相矛盾」——读它的工具按分组走，读注释的人按注释走。

它们的标识符也因此**受 ≤7 字符规则约束**（`Sapling` / `Rubble` / `Stump`）：
CLAUDE.md 那条豁免的前提是「不进任何枚举、不被仿真引用」，而有血量就是被仿真引用。
`ForestB` 同理——它既被声明为 `Forest` 的贴图变体，键就必须是 `Forest*` 前缀，
否则渲染层挑变体时无从归类（写法同 `PlainB`）。

**登记新实体前先跑一遍校验**：

```bash
python check_assets.py    # 模型是否存在、有没有和别人共用主体、产物与元数据是否一致
```

它拦两类坑。

**第一类：两个机制完全不同的实体共用一张图**，已经踩过两次：
采石场与岩壁同为 `rocks-large`；伐木场与**木栅**同为 `wall-narrow-wood-fence`
（木栅是波次中可即时放置的应急工事，与经济建筑机制完全不同）。
`models/` 下有一百多个文件、`assets.json` 有三十多个实体，
靠人记得"这个模型有没有被别人用过"不现实。

「配件用了别人的主体模型」只**提示不失败**——岩壁含碎石、密林含小树是构成关系而非误导，
只有配件大到能被读成独立实体时才是问题，而那没法用规则判。
**一个总是红的检查等于没有检查**，人会连带无视真正的硬失败。

**第二类：`out_3d/` 与 `_sprite_meta.json` 对不上。** 两个方向都查：

| | 怎么产生的 | 症状 |
|---|---|---|
| **孤儿**（磁盘有、元数据没有） | 改了某状态的 `frames`，`--only` 重渲只覆盖同名文件、不删旧的 | **纯静默**——元数据对、取图也对，只有交付包多带一批没人引用的图 |
| **缺失**（元数据有、磁盘没有） | `--only` 渲了一半中断，元数据已写、文件没齐 | 前端运行时报文件找不到，而那时人会**先怀疑前端** |

孤儿那条是实测踩到的：`Spear` 的 `frames` 从 `[1,7,11,16]` 改成 `[1,7,13,19]`，
留下八张 `_11` / `_16`。

七条踩过的坑，换素材时大概率还会撞上：

- **主体模型不能和任何别的实体撞。** 见上，用 `check_assets.py` 挡。

- **先渲一张构件对照表再设计，不要照文件名猜。** 本包里
  `tower-slant-roof` **不是屋顶构件，是一整座带门的尖顶小屋**；
  `wall-narrow-wood-fence` 是靠墙的木晾架、直接就能当伐木场；
  `tower-square-arch` 是四腿石拱架。而 `tower-square-base` 是**塔的地基**——
  没门没顶的方块，单独放既难看又和城墙同色。凭名字设计连着做废了两版。
- **共用主体 + 小配件是行不通的。** 试过三座共用一个砌体基座、只靠贴地的加工构件
  与旗区分——等距下那些配件根本看不见，三座读作同一个方块。
  **区分必须做在主体形体上。**「攻其必救」是头号演示点，
  前提是观众看得出 AI 奔着采石场去。
- **共用主体 + 染色同样行不通，而且这条更隐蔽。** `Watch` 曾与三座砌体塔共用
  `tower-square-base/mid/top`，靠 `tint` 染棕来表示「木材造」，渲出来是**一根刷了
  棕漆的石柱**：染色只改色相，改不掉「实心砌体」这个形体。改用镂空木架后问题消失，
  而且**新条目一处 `tint` 都没有**——木色是 `tower-square-mid-open-simple` 的构件本色。
  实测过的四种染法（`COLOR`+压暗、`MIX`、`MIX`+压暗、只压暗）**全都比不染更差**，
  把浅色砌体压暗只会从「石板」变成「泥板」。
  一般规律：**材质感属于形体与本色，染色只该用来分阵营**（见「阵营配色」一节）；
  发现自己在用 `tint` 表达「这是什么材料造的」，就说明选错了构件。
- **旗要放在 `-x / -y` 那一侧**，那是面向相机的一面。曾把三面旗放在 `+y`，
  结果全被建筑本体挡住、一面都没渲出来。旗色 = 产哪一种（石灰 / 木绿 / 金黄），
  因为按 CLAUDE.md「交错杂居」，**一簇内本就混有石木金，相邻的异种资源建筑是默认布局**。
- **高度必须与机制同向。** `Sapling` 曾登记为 `modules: 1.4`，
  **比密林 1.25 还高**——一株细树比一整片林子高，「矮 = 可破坏」在画面上直接反了。
  这类错误单看一张图看不出来，**必须按锚点把两族排在一起才会暴露**。
- **改过某个状态的 `frames` 之后要删旧帧号的文件。** `--only` 重渲只覆盖同名文件、
  不删旧的，于是 `[1,7,11,16]` 改成 `[1,7,13,19]` 会在磁盘上留下八张孤儿 PNG。
  症状是**纯静默**的：元数据是对的、前端按元数据取图也是对的，只有交付包会多带
  一批没人引用的图——而那恰是交付清单要求精简的东西。`check_assets.py` 现在会红。

## 攻击动画：三条只有渲出来才知道的事

**这一节全部来自实测**，做法是先渲一张宽采样对照表再挑帧，而不是照动作名猜
（这条纪律在上面的资源建筑那一轮已经交过学费）。

### 1. 各单位的攻击动作**不是都有**

| 单位 | 可用动作 | |
|---|---|:-:|
| `Archer` | **`Bow_Attack_Draw` + `Bow_Attack_Shoot`**（两段） | ✅ |
| `Spear` | `Sword_Attack` / `Sword_AttackFast` | ✅ |
| `Ranger` | `Dagger_Attack` ×2（骑手部件） | ✅ |
| `Ghoul` / `Knight` | `Skeleton_Attack`（**共用**，见第 2 条） | ✅ |
| `Mason` | `Staff_Attack` —— 读作**敲打**，正好当维修 | ✅ |
| `Shade` | 只有 `Skeleton_Attack`（近战挥砍）**而它拿着弓**——用它的 f7–f16，那段恰好是一套射箭序列，见第 6 条 | ✅ |
| `Phoenix` | Eagle.blend 只有 `Flying` / `Idle`，**没有攻击**——改用**整体俯仰**，见第 5 条 | ✅ |
| `Ram` | Kenney 件**零动作，但有可分离的子网格**——改用子网格变换，见第 4 条 | ✅ |
| `Flak` | 顶上那台投石机**有可分离的 `arm`**——摆抛臂即可，见第 4 条 | ✅ |
| **`Tower`** | 全是单网格塔块，**无可动部件**——改用**垛口上待发的箭**，见 2.2 | ✅ |
| `Scout` / `Wraith` | 有，但零战力、不需要 | — |

**「零动作」不等于「做不了动画」。** 第一版这张表把 `Ram` 与 `Phoenix` 都判成 ❌，
理由是「素材包没有攻击动作」——那是**只查了动作数**。查动作之外还要看两件：
**有没有可分离的子网格**（`Ram`：撞木 + 六个轮子各自独立），
以及**这个动作是不是本该由姿态而非动作表达**（`Phoenix` 的俯冲是整只鸟的姿态）。

**弓手那两段是接得上的**：`Bow_Attack_Draw` 结束在满弓，而 `Bow_Attack_Shoot`
的首帧正是同一个满弓姿态。所以 `attack` 只取 `Shoot`——前端在前摇期间**保持首帧**
（满弓待发），前摇结束再播到松弦，正好落在 `impact_frame` 的用法上。
不取 `Draw` 是因为「把弓举起来」这个过程本身就是在用动画表达时长，而时长是待定数值。

### 2. 那五个 ❌ 现在一个不剩

第一版把 `Shade` / `Phoenix` / `Ram` / `Tower` / `Flak` 五个都判成「攻击表现属
`render/` 的弹道，本流水线做不了」。**评审逐个追问之后，四个被做出来了；
第五个（`Tower`）在 2026-08-30 也做出来了，见 2.2。** 五条路子各不相同，值得逐条记：

| 谁 | 原判 | 实际的办法 |
|---|---|---|
| `Ram` | 静态网格 | **有可分离子网格**——撞木滑动（第 4 条） |
| `Flak` | 静态网格 | 顶上投石机**有可分离的 `arm`**——摆抛臂（第 4 条同一机制） |
| `Phoenix` | 没有攻击动作 | 俯冲**本该由姿态表达**，不是动作（第 5 条） |
| `Shade` | 只有近战挥砍 | **同一个动作的 f7–f16 就是一套射箭序列**（第 6 条） |
| **`Tower`** | 「确实做不了」 | **垛口上待发的箭**——塔身完全不动（2.2） |

共同的教训是**「零动作」不等于「做不了动画」**。至少要再查三件：

1. **有没有可分离的子网格**（`Ram` 的撞木、`Flak` 的抛臂）
2. **这个动作是不是本该由姿态而非动作表达**（`Phoenix` 的俯冲）
3. **可读性能不能由武器/挂件承担，而不必动身体**（`Shade` 的弓、骑兵的刀）

### 2.2 `Tower` 那条「确实做不了」也被推翻了，而推翻它的是上面第 3 条

这一条最值得记，因为**答案就写在同一节里**：第 3 条自查说的是
「可读性能不能由武器/挂件承担，**而不必动身体**」——`Shade` 就是这么做的
（转武器、身体不动）。而我写下这条之后，仍然把 `Tower` 判成
「没有可动部件 ⇒ 做不了」，并且那句判断在这份文件里活了两周。

**「塔身不能动」与「攻击表现做不了」是两件事**，中间缺的那一步正是第 3 条。
（触发这次复查的是评审一句「tower 缺攻击动作」。）

做法：`only_meshes` 提一支箭放到垛口，`mesh_anim` 控制可见性——
`idle` 不可见、`attack` 首帧可见（待发）、`impact_frame` 那帧消失（离弦）。
与 `Archer` 弦上那支箭**逐字同构**，用的还是同一个 mesh。

**原判的后半句仍然成立，而且现在两段接上了**：256 px/瓦片下塔身的「后坐」只有
几个像素，真正告诉玩家「它在开火」的是飞出去的那一发。所以完整表现是**两段**：

| 段 | 谁负责 | 状态 |
|---|---|---|
| 垛口上待发的那支箭 | 本流水线（`Tower_attack`） | ✅ |
| 飞出去的那一发 | `render/` 的弹道 + `Arrow` 精灵（§8.3） | 精灵已入库，绘制待 PR F |

**两段用的是同一个 mesh**，所以离弦那一刻的交接是连续的——这一点是免费拿到的，
因为弹丸精灵当初就刻意复用了弓手弦上那支箭（§8.1）。

弹道更服务机制可读性这条也不变：`Tower` 是齐射覆盖、`Flak` 是单体狙击，
两者作为**弹道**天差地别（一片箭雨 vs 一条曳光），作为**塔身动画**毫无区别。
所以垛口那支箭只表达「在开火」，**不表达「齐射」**——后者归弹道。

### 2.1 `Flak` 为什么不换成弩炮，尽管「单体狙击」的机制更像弩

这一处我差点推翻一个**记录在案且正确**的旧决定，过程值得写下来。

`Flak` 是「蔽空**弩**楼，**仅对空**，**单体狙击**」，而它顶上装的是**投石机**——
投石机的视觉语言是抛射覆盖，`CLAUDE.md` 还明写「AA 只做单体狙击型，不做群伤型」。
`siege-ballista.glb` 恰好是直射单体、名字对得上、**而且有可分离的 `arrow` 子网格**。
看起来该换。

但 `assets.json` 里那条 `_note` 早就写了不换的理由：

> 弩炮/投石机都带轮子，堆在塔顶读作「地面载具」，**只有这条斜向长臂在小尺寸下
> 仍读得出「朝天」**

**实测了才知道这条是对的**：弩炮无论仰 0° / 25° / 40° / 55°，在这个尺寸下都是一台
低平的装置，读不出「朝天」；而投石机的斜向长臂一眼就是。

真正把两者分开的是**哪一位信息值得占用剪影**：

- **「仅对空」是玩家的决策**——`CLAUDE.md`：「每座 AA 都意味着该位置少一座对地火力」，
  玩家必须一眼看出哪座塔放弃了对地。这一位必须可读
- **「单体 vs 群伤」不是玩家的决策**——AA 只有一座，玩家没有可选项。
  那是一条**对我们的设计约束**，不是玩家要从画面上读的信息

所以不换。教训：**改一个记录在案的决定之前，先把它的 `_note` 读完**——
它写下来正是为了防止这种「看起来显然该改」。

### 3. 骑兵：骑手被 `pose` 冻住是**必然**，不是偷懒

试过一版 `pose_live`：保留动作、只在每帧渲染前把手工骨骼角度盖回去，
让骑手跟着动作动起来。**渲出来更差，已放弃**，理由值得写下来——

`pose` 里手工覆写的只有腿（大腿前摆、小腿外张，绕开马腹），而**髋与脊椎跟着动作走**。
`set_pose` 清除动作时，是把**整个骑手**连髋一起冻在那一帧；一旦让动作继续驱动，
髋的高度就不再固定，骑手**下沉进马身**，于是那双掰开的腿又插进马腹——
正是 `pose` 当初要解决的那个 bug 原样回来。

要做对得把髋也钉住，而那是**逐单位调参**（每个骑手 / 每匹马的比例都不同）。
收益是「骑手在奔驰的马上挥一下手臂」，而那在 40 px 高的剪影上几乎看不出来。
比例不对，所以不做。

**因此攻击态靠转武器而不是换动作**：

给骑手换成攻击动作**没有用**——`pose` 会清除动作、把骑手定格，而
`Skeleton_Attack` 几乎不动手臂，于是 `Knight` 的攻击态和移动态肉眼无法区分
（第一版正是如此）。

改用**在攻击态里覆写武器部件的 `rot`**：武器是剪影里最长的元素，等距下最读得出。
`Knight` 从「收在肩前」转成**前刺的长刀**（`-105°` → `-75°`），
`Ranger` 从贴身转成**前伸横持**（`0°` → `-60°`）。角度是试出来的：
先试 `-165°`，刀刃指向后上方，会被读成「剑背在背上」，方向反了。

### 4. `Ram` 与 `Flak`：`mesh_anim` —— 按名字对**子网格**做逐帧变换

`siege-ram.glb` 的结构是：

```
MESH 'siege-ram'              车体
  MESH 'ram'                  撞木（2.09 × 0.21 × 0.21，长轴沿 X）
  MESH 'wheel' … 'wheel.005'  六个轮子（0.40 × 0.13 × 0.40，薄在 Y ⇒ 轴是 Y）
动作数: 0
```

于是撞木沿 X 滑动 = 撞击、轮子绕局部 Y 转 = 行进，两者都是**纯物体变换**。
`mesh_anim` 的键支持末尾通配（`wheel*` 命中六个）。

**两处踩过的**：

- **`pivot_center` 是必需的，不是可选优化。** 旋转绕的是**对象原点**，而素材里原点
  常常不在几何中心——`wheel` 的原点在 `(0.67, 0.5, 0)`、几何中心在 `(0.47, 0.43, 0.20)`，
  直接转它得到的是**绕车体公转**而不是自转，看着像轮子往外甩出去。
  症状只在多帧并排看时才显形，单帧完全正常
- **静止态也要把撞木推出去一截。** `Ram` 是「玩家的头号集火目标」，
  静止时也必须一眼认出是攻城锤——不推的话撞木藏在屋顶下，整个读作一辆带篷的车

`mesh_anim` 还支持 `visible`（逐帧显隐），弓手弦上那支箭靠它在**命中帧之后消失**。

**同一机制也给了 `Flak` 攻击态**：`siege-trebuchet.glb` 里 `arm`（1.76 长，原点在
转轴上）是独立网格，摆它即可——后拉 `-30°` → 过中 `0°` → 抛出 `+60°` → 回落 `+25°`。
`idle` 保持 `0°`，所以**既有的 idle 精灵一张都没变**。
配重与吊斗是 `arm` 的**兄弟节点不是子节点**，所以不随之摆动；这个尺度下
抛臂自己已经承担了全部可读性，没必要再动它们。

### 5. `Phoenix`：顶层 `rot` —— 有些动作本该由**姿态**表达

Eagle.blend 只有 `Flying` 与 `Idle`。俯冲不需要一个「攻击动作」——它是整只鸟的姿态：
顶层 `rot` 把机身下压 50°，配 `Flying` 中翅膀后掠的几帧。

**`lift` 刻意与其余状态保持一致。** CLAUDE.md 靠「本体与投影的间距」让玩家分辨
`Wraith`（地面）与 `Phoenix`（空中），而那是一条**结构性**区分；
俯冲时压低 `lift` 会让空中单位在最关键的一刻看起来像地面单位。
俯冲由机身姿态表达就够了。

`rot` 是**状态可覆写**的。第一版放在实体级，结果 `idle` 与 `move` 也被压了 50°
——一只永远在俯冲的鸟。

### 6. `Shade`：**只查了一帧就判整个动作不能用**，代价是它两周没有攻击表现

亡灵弓手拿着弓，而骷髅**只有 `Skeleton_Attack`（近战挥砍）**。本节初版这么记：

> 用那个动作试过，**f19 骷髅弯折成一团、是坏帧**。

于是退回「身体保持 `Skeleton_Idle` + 只把弓转个角度 + 箭消失」。**那一版被评审一句
「亡灵弓手攻击动作不像攻击」打掉了，而它完全说对了**——`attack` 的
`parts.0.action` 就是 `Skeleton_Idle`，和 `idle` **逐字相同**，
四帧只是待机循环的四个相位。**画面上就是站着不动。**

**把整个 0–28 帧铺开渲一遍才看清**：坏的是**后半段**（f22 / f25 / f28 骷髅整个
弯折变形），而 **f7 / f10 / f13 / f16 恰好是一套「举弓 → 拉满 → 瞄准 → 放」
的完整序列**。

> **「某一帧坏」不等于「整个动作不能用」。** 一个 29 帧的动作，只查了 f19 就下结论，
> 而结论的形式是「没有射箭动作」——**一个否定性的、听起来已经穷尽的判断**。
> 这与 2.2 那条（`Tower`「确实做不了」）是同一个形态：**用一次局部失败
> 推出一个全局不可能**，然后那句话就不再被复查。

现在的配置：`frames: [7,10,13,16]`、`impact_frame: 13`、弓 `rot: [-70,-30,90]`，
外加 `mesh_anim` 让弦上那支箭在**命中帧之后**消失（与 `Archer` 同一约定：
命中帧箭仍在弦上，下一帧才空）。弓与箭同在 `Ranger_Bow.blend` 里，本来就有。

**弓为什么斜持而不竖持。** 试过 `[-90,-90,90]`（竖立），**弓侧对镜头、又变成
本节开头那条「看不出是什么的细线」**——那正是这个单位最早的缺陷，差点原样重犯。
斜持时弓的弧形完整可见，而「弓读得出是弓」是硬要求：`Shade` 是「持续压制墙头」
的那个单位，玩家要能一眼数清编成里有几个远程。

**已知余项**：`NE` 朝向弓被头挡住大半。那是**姿态本身**的问题、不是 `rot` 能修的
（举弓过头 + 侧身），另三个朝向都完整。暂按可接受处理。

这条与第 3 条（骑兵）合起来仍是同一句：**在这个分辨率下，武器比身体好读**——
但那句话不能被用来免掉「身体也该动」。

### 7. 「地面 vs 城墙」的区别**不做成精灵变体**

驻守槽位在机制上确实不同（射程加成、高度惩罚、被钉在那一段），所以想过给
`Archer` 做一个墙上俯射的姿态。**渲出来验过，放弃**，三条理由：

1. **`Torso` 旋转产生的是侧向后倾，不是俯射。** 这个骨架的局部 X 轴不是前倾轴，
   而 45° 相机把任何单轴倾斜都变成对角歪斜——试了 `-20/-35/-50°`，三个都读作「向后靠」
2. **即使找对轴，量级也不够。** 手臂角度变化在 250 px 高的精灵上约 10 px，
   远不如「画在墙顶上」这个位置差异清楚
3. **`pose` 会清除动作**，所以墙上变体只能是**一张静止帧**，而地面是 4 帧动画——
   在墙头这个主战场上反而是质量倒退

**承担这个区别的应当是位置与图层，不是身体姿态**：抬高绘制 + 深度序排在墙段之后。
两者都是 `render/` 免费拿到的，`preview_map.py` 的 `draw_scene()` 已经是这个结构。

### 8. 在途弹丸**撤出了本流水线**，理由是契约不是数值

做过一版 `projectiles` 分组（`Arrow`，复用弓手弦上那支箭的模型，
`kind: "projectile"` 只描边不画地面投影）。**渲出来发现四个量化朝向表达不了它**：

```
Arrow_idle_SE  内容 66×42   SW  26×20   NE 71×41   NW 74×42
```

SW 被压缩到不足一半——**三长一短**，说明箭并没有落在水平面里，
而某一个朝向恰好接近视线方向。

但真正的问题比「调不对角度」深一层：**弹丸的飞行方向是连续的**，
四个固定朝向本质上表达不了。

可选的做法有两条，而**选哪条是契约决定、不是本流水线能单方面定的**：

| 做法 | 代价 |
|---|---|
| 单张精灵 + 前端按飞行角 2D 旋转 | 需要给弹丸开「每实体自己的 `dirs`」这个口子，动元数据契约 |
| 多档俯仰 × 多档朝向 | 图数量按乘积增长，且档数取决于弹道形状——那还没定 |

所以这块留给 `render/`（@zhxxx233 已在 #42 提出弹道缺一条接口信息：
「这次攻击的目标是谁」）。`only_meshes` 与顶层 `rot` 两个能力保留在流水线里——
它们已经被弓手弦上的箭与不死鸟的俯冲用上了。

#### 8.1 这节原来的论据里有一条是错的，而它把清单撑大了

本节初版在「飞行方向是连续的」后面跟了一个括号：「`CLAUDE.md` 明写 `Ram` 的弹道有
飞行时间，而 AOE 落点与散开的单位有关，所以那个弧线是仿真的一部分」。**那句已删。**

`Ram` 是**贴身撞锤，没有弹丸**（2026-08-29 定案；CLAUDE.md 原写「弹道有飞行时间」
与花名册那一列的「贴身」自相矛盾，已改正）。所以：

- **本流水线一直是对的**——§2 那张表把 `Ram` 做成「撞木滑动」，按的就是撞锤。
  **实现比描述更早地做对了**，错的只是本节引来当论据的那句文字
- **「弧线」这条也一并撤**：三种真有弹丸的都是直射，没有抛物线要表达

于是清单是**两种，而不是原先以为的四种**。它缩过两次，第二次的理由比第一次要紧：

| 弹丸 | 谁用 | 内容框（实测） | 视觉 |
|---|---|---|---|
| `Arrow` 箭 | `Archer` / `Shade` / `Tower` | 84×9，比 9.33 | 木羽箭，复用双方弦上那支 |
| `Bolt` 弩矢 | `Flak` | 56×11，比 5.09 | 短粗、大金属箭头 + 木色杆 |

**第二次缩掉的是「守方箭 vs 攻方影矢」那一条分法，它是错的。** 曾按阵营分成两种，
但 `CLAUDE.md` 说「机制信息由视觉剪影与 UI 承担」，而**阵营不是机制信息**——
守方箭与攻方箭的机制完全相同（都是中程单体），且**飞行方向已经区分了它们**
（守方的往外飞、攻方的往内飞）。在一个 9 px 厚的飞行物上再叠一层颜色编码，
玩家读不出来，也没有需要它支撑的决策。

真正该由剪影承担的是 `Arrow` vs `Bolt`——**轻箭 vs 重狙击弹**，那对应
「`Flak` 仅对空、单体狙击」这条真实的机制差异。两者的内容框比 9.33 vs 5.09、
形体一细长一短粗，小尺寸下也分得开。

顺带一个发现：**`Archer` 与 `Shade` 弦上那支箭本来就是同一个 mesh**
（都从 `Ranger_Bow.blend` 提 `Ranger_Arrow`），只是 `Shade` 的弓 part 整体染了棕色
顺带染到箭。所以「射出去的和弦上那支是同一个形体」是免费拿到的，
而按阵营分反倒要**额外**造一个差异出来。

**已知未处理**：因为那个染色，`Shade` 弦上是棕的、飞出去的 `Arrow` 是灰白的。
9 px 的差异，且要修得把 `Shade` 的箭拆成独立 part 再重渲它 20 张图，
比例不对，暂按可接受处理（同本文件其它「已知未处理」条目）。

`Flak` 那条看着不协调——**发射器是投石机造型，弹丸却是单发直射**。但按 §2.1 自己的
逻辑这是对的：那节的结论是「仅对空」这一位必须占剪影、「单体 vs 群伤」不必。
**弹丸正好补上剪影没表达的那一位**，两位信息各占一处，不冲突。

`Phoenix` 的俯冲是姿态（§2、§5），近战四个与三个无战力单位都不需要弹丸。

#### 8.2 撤退的两条理由现在一条已经不成立

上表第二条（多档俯仰 × 多档朝向）的阻塞仍在：档数取决于弹道形状。
**但第一条的代价比当时估得便宜，而且它恰好绕开了第二条的阻塞：**

1. **元数据契约现在只有一个读取点。** `render/include/render/sprite_atlas.hpp`
   明写「本类是这个字段在 C++ 侧的**唯一**读取点」。当时那条「动契约」的顾虑是按
   多处读取估的；改一个单读取点的契约，代价是有界的
2. **2D 旋转不依赖弹道形状。** 角度是运行时按飞行方向算的，直线还是弧线都能画。
   所以它满足 CLAUDE.md 那条「接口与回放格式的承诺不得依赖任何待定数值」——
   而多档俯仰那条恰恰违反它：**档数是一个待定数值，会被烤进资产**

**代码通路还留着**，撤掉的只有 `assets.json` 里的分组条目：
`check_assets.py` 与 `blender_render.py` 的分组循环里 `projectiles` 都在，
`postprocess.py` 那条 `kind == "projectile"`（只描边、不画地面投影）也在。
所以重开工是**加回一个 JSON 分组 + 把 `dirs` 开成每实体可覆盖**，不是重写流水线。

### 8.3 已经做了（2026-08-30）。`FREE` 是怎么定的，以及它带出来的三处硬编码

**`dirs: ["FREE"]`** —— 这个朝向名不是一个方位，它表示「**这张图不承诺任何朝向**」。
图渲成横躺、箭头朝屏幕右（+X = 0 弧度），方向由前端按飞行角 2D 旋转。

`DIR_YAW["FREE"] = 45` 是**推导出来再实测确认的**，不是试出来的：相机
`rotation_euler` 是 `(PITCH, 0, YAW)`，于是屏幕水平轴（相机 local +X）在世界里是
`(cos YAW, sin YAW, 0)`；让模型长轴与它平行，投影后就水平。part 的
`rot: [0, 90, 0]` 负责先把模型竖直的长轴转成 +X——**这一步是渲出来才知道要加的**
（不加时内容框 9×51，箭是竖着的）。

**`SE` 那个 0° 不能拿来当起点**：它让箭在屏幕上斜着（初版四向那次的 66×42 就是），
前端旋转时得先减掉一个未写在任何地方的固有偏角，漏掉的症状是
「箭大致朝目标飞、但总歪一个固定角度」——那看着像弹道算错、不像资产不对。

#### 弹丸的旋转中心是 `pivot`，**不是 `ground_anchor`**

元数据给 `kind == "projectile"` 的条目多写一个 `pivot`。这条是渲出来测了才发现的：
`ground_anchor` 是**世界原点**的投影（代表「实体脚底」），而 `normalize()` 把 bbox
中心移到原点之后 `pivot` 又绕自身 location 转了 45°，于是原点的投影与箭的视觉中心
**实测差 19–26 px**。拿它当旋转中心，箭会绕一个偏离自身的点公转。

> **这个错在静态精灵上完全看不出来**，只有转起来才暴露——所以它必须由检查守，
> 不能靠出图时目视。

`pivot` 取的是**几何 bbox 中心**（`mesh_center_px()`），而不是 alpha 内容框中心：
后者受抗锯齿影响（箭尖最后几个像素 alpha 太低会被 `getbbox()` 丢掉，实测让
`Arrow` 偏 1.9 px），前者不随渲染参数变。alpha 中心只用来**验证**。

#### 同一个四朝向名单原来写在三处，加 `FREE` 时三处都坏

这是这次改动里最值得记的一条：`{"SE","SW","NE","NW"}` 被硬编码在

| 处 | 症状 |
|---|---|
| `render/src/sprite_atlas.cpp` `verify_all_declared()` | 报「缺 8 张素材」——而那 8 张本来就不该存在 |
| 同文件 `preload_idle()` | 只修上面一处的话：**校验通过但预载失败** |
| `check_assets.py` `check_orphans()` | 同时报两遍同一件事：`_FREE.png` 是「孤儿」、四张 `_SE/_SW/…` 是「缺失」 |

三处现在一律改成按实体取（`dirs_of(ident)` / `spr.get("dirs", meta["dirs"])`）。
**教训不是「别硬编码」这种空话**，而是：一个常量写在三处时，
「加一个新取值」这件事会**分三次**失败，而中间那次的症状
（校验绿、预载红）看起来完全不像同一个原因。

#### 两条永久检查，都做了破坏性验证

`check_assets.py` 新增 `check_projectiles()`：

1. **必须横躺** —— 内容框宽高比 ≥ 3.0。实测 `Arrow` 9.33、`Bolt` 5.09
2. **`pivot` 必须落在图上** —— 离 alpha 内容框中心 ≤ 4 px。实测偏 1.9 / 0.4 px

四次破坏性验证（照 `determinism_bans_self_test` 的规矩，不留永远绿的检查）：

| 破坏 | 结果 |
|---|---|
| `pivot` 挪 30 px | 红 ✓ |
| 删掉 `pivot` | 红 ✓ |
| 把图转 90° | 红 ✓（比 0.15） |
| 把图转 **30°**（隐蔽的斜） | 红 ✓（比 1.59） |

最后一条最有价值：**斜 30° 只让宽高比掉到 1.59**，说明 3.0 这个阈值既有余量、
又抓得住肉眼未必立刻看出的偏斜。全部恢复后检查转绿。

#### 顺带修了 `postprocess.py` 一处「该报错却崩溃」

`contact_sheet()` 原来用全局 `dirs` 拼文件名，弹丸一张也匹配不上，于是组为空、
下一步崩在 `max()` 上——**traceback 指向那一行，完全看不出真因是朝向对不上**。
真因已修（按实体取），另加一条防御：空组改为逐个报警告并跳过，
因为「手删过几张图」「元数据比图新」同样会造出空组。

**浅色构件染色后要额外压暗。** `COLOR` 混合照抄原纹理明度，而 Kenney 的砌体件本色偏白，
只染色相会读作石膏而不是花岗岩；石拱架配 `brightness ≈ 0.7` 才对。同一条已在
水域地砖上撞过一次（见上）。

`ForestB` 是 **`Forest` 枚举的贴图变体**（单株巨树占满一格），不是独立枚举值、
也不是纯装饰——机制与密林相同，渲染层按坐标哈希在「三株成簇」与「单株巨树」
之间选，写法同 `Plain` 的四个变体。

**已知未处理**：资源建筑的浅色砌体与 `Wall` / `Gate` / `Barrack` 同料，
位置与旗色能区分，但不如与自然物的区分强。属另一条轴，暂按可接受处理。

试过用 `ground-hills.glb` 做起伏地砖，**失败**：0.29 的隆起在等距视角下读作草地上的
绿疙瘩而不是地面起伏，反而破坏了地面的连续感。改用同色微差的第二种草地供交错铺设。

**平面地砖的染色要额外压暗。** 朝上的漫反射面在三点光下会被打得很亮，
水域按 `MIX` 混到饱和蓝仍会渲成灰蓝，须配 `brightness ≈ 0.5` 才读得出是水。

## 线性结构的朝向是**走向**，不是朝向

单位的 `d` 是它面朝哪；**墙、桥这类线性结构的 `d` 是它沿哪个方向铺**。
同一段墙沿 `gi` 铺和沿 `gj` 铺要取不同的精灵，否则相邻段接不上——
一条城墙读作一排分开的板子。

哪个朝向无缝是**实测出来的**（四个朝向各排三格，看哪个接得上）：

| 走向 | 用哪个朝向 |
|---|---|
| 沿 `gi` | `SW` |
| 沿 `gj` | `NW` |

`preview_map.py` 的 `run_dir()` 就是这两行，前端照抄即可（真实前端应当按邻居推导，
和自动拼接地砖是同一套做法）。**换素材后要重测**——这取决于模型自身的长轴朝向。

塔、堡垒这类回转体不受影响，朝向随便取。

## 场景预览：前端契约的可执行示例

```bash
python preview_map.py out_3d
```

`preview_map.py` 读 `_sprite_meta.json` 拼出一张 15×15 的等距场景。脚本本身分成两段：

**「契约」一段**是写前端时该照抄的：

- `grid_to_screen()` —— 等距的全部数学就两行
- `place()` —— 把**锚点**对齐到格心，而不是把图片左上角对齐到格心。
  各精灵画布尺寸不同，按左上角贴会让高个子单位整体上浮
- `expand()` + `OVERLAY` —— **一格要画两张图**：底衬地砖 + 可选叠加物件。
  `地图与场景设计.md` 4.2.1 声明这张表是该映射的规范来源
- `run_dir()` —— 线性结构按走向取朝向（见上一节）
- `draw_scene()` —— 两遍：先整片铺地砖（平的、不遮挡），
  再把叠加物件与单位混在**同一个**深度序列里按 `gi+gj` 排。
  岩壁与单位必须一起排，否则站在岩壁前的单位会被岩壁盖住

**「演示地图」一段**与契约无关，只为把设计摆出来看：城圈 + 缺口、天然岩壁承担后半周、
三条性质不同的走廊、城内三种资源点、墙外资源簇 + 森林带、河与桥、攻守双方。
它同时是**相邻摆放的目视校验**——单看每张精灵都没问题，撞色撞形与比例错只在相邻时暴露。

### 摆位受等距遮挡支配，不能只照设计图摆

这条连着做废了两版布局，值得单独写：

- **高物件放在前排会把后面一切埋掉。** 第一版按 2.2「天然岩壁承担大部分周长」把
  1.5 模数的岩壁摆满整圈，结果城内的堡垒、资源建筑、单位全被埋了。
  规则是：**岩壁只放后半弧（`gi+gj` 小），面向相机的两条边留给矮的城墙。**
- 同理，对岸那簇资源**不能铺森林带**——1.35 模数的树在桥头会把桥和矿场一起埋掉。
- **城墙不能一条边砌满。** 一条边七块同样的板子读作栅栏；每隔几格嵌一座塔才像城墙，
  而这也正是 2.2 说的「只有走廊口需要人工墙」。
- **桥面必须是低平的。** `bridge-straight` 在这个尺度下是一块带雉堞的浅色砌体方块，
  与城墙同料同高，摆在水面上读作「河里立了一段墙」；换成 `bridge-draw` 的平木板才对。
  而且**河至少两格宽**——一格宽的河上放桥读不出「跨过去」。

已知性质：地砖边缘的抗锯齿会让相邻格之间留下一条极淡的缝，看起来像一层网格。
本项目地图本就是 grid，暂按可接受处理；若要消除，前端把地砖放大 1~2 像素绘制即可。

默认输出缩到 2600 px 宽（够看且不撑大仓库），`--full` 出原始分辨率。

## 为什么混用不同来源不会翻车

混用 **2D** 等距精灵几乎必然翻车——投影角、比例、光照方向已经烤死在像素里，无法统一。

混用 **3D** 模型则可以救：所有模型都经过**同一个正交相机 + 同一套三点灯光 + 同一分辨率**，
再统一缩放到规定高度。风格差异在渲染阶段就被压平了。这正是选择预渲染路线的原因。

## 关键约定

- **相机俯角 30°**（绕 X 60°、绕 Z 45°），投影瓦片为 **2:1**。改这个值等于改掉整套素材。
- **旋转模型而非旋转相机。** 相机与灯光固定，各朝向受光不同，符合等距游戏观感；旋转相机会让模型受光恒定，画面发平。
- **描边与地面投影在后处理做，不在 Blender 做。** 描边保证暗色单位在暗色地表上剪影可读；地面投影同时承担"表达高度"的职责——空中单位投影留在地面、本体抬高，玩家一眼看出它在飞。

## 前端契约：`_sprite_meta.json`

随精灵输出，**这是前端唯一应当依赖的尺寸约定**：

```json
{
  "px_per_tile": 256,
  "sprites": {
    "Spear": { "cn": "铁壁枪卫", "states": {
      "idle": { "canvas": [302, 406], "ground_anchor": [151.0, 297.4], "frames": [1] },
      "move": { "canvas": [374, 466], "ground_anchor": [187.0, 337.6], "frames": [1,6,11,16] }
    }},
    "Wall": { "cn": "城墙", "states": {
      "idle": { "canvas": [332, 456], "ground_anchor": [166.0, 344.5], "frames": [1] }
    }}
  }
}
```

文件名是 `<标识符>_<状态>_<朝向>[_<帧号>].png`，**单帧时无帧号后缀**。
建筑等静态实体也有 `idle` 状态，前端因此不必对它们特殊处理。

`canvas` 与 `ground_anchor` **按 (标识符, 状态) 读取**：不同状态的画布大小不同
（奔跑时四肢伸展更占地方），但锚点始终对齐同一个地面点，所以 idle↔move
切换时精灵不会跳动。

**画布尺寸逐个实体适配，因此 `canvas` 与 `ground_anchor` 必须按精灵读取。**

实体高度跨度约 5 倍（幽影窥使 0.45 瓦片 ~ 领主堡垒 2.15 瓦片）。统一画布只能二选一：
要么裁掉高的，要么把矮的挤成一小点。因此本流水线**固定世界→像素缩放**（`px_per_tile`），
只让画布随实体变化——相对大小因此始终正确，单位本就应当显得比塔矮。

画布由 `frame_for()` **把归一化后的几何投影到相机平面实测**得出，不按声明尺寸估算。
早先按 `height` / `max_width` 估算有两个错处，都只会静默地裁掉画面而不报错：

- 等距投影下**水平位移也会产生纵向的屏幕位移**。骑兵又长又矮，纵向占位远大于其
  `height`，按高度定画布会裁掉马蹄
- `max_width` 是归一化的**上限**而非实际宽度，步兵的画布因此宽了近一倍

底部另留出投影余量（`SHADOW_PAD`），否则宽实体的地面投影会被下边缘切掉半个。

`ground_anchor` 是画布内**代表实体脚底的像素坐标**，前端据此把精灵对齐到格子中心。

- 由**相机投影精确算出**（世界原点的投影位置），不是估算
- **不要靠 alpha 包围盒底边推算**——实体带披风、长矛、尾羽、旗帜时会明显偏移
- 后处理画地面投影也用它。空中单位抬升后，本体与投影的间距即"飞行高度"

`--only` 部分重渲时元数据会与已有条目**合并**，不会丢掉其余精灵。

## 后处理是幂等的

`postprocess.py` 默认原地覆盖输入目录。为避免重复运行不断叠加描边与投影（且**不报错**，只是一次比一次糟），处理过的 PNG 会写入文本标记 `siege_postprocessed`，再次运行时自动跳过。

`--force` 可强制重处理，但**只应对未经后处理的原始渲染输出使用**。

## 精灵成品入库

`out_3d/` 的 **476 张**精灵（35 实体 × 4 朝向，状态数逐实体不同：
`idle` 140 + `move` 176 + `attack` 144 + `work` 16）、`_sprite_meta.json` 与
场景预览图 **入库**，理由三条：

1. 交付清单要求「软件源代码**包括输入文件和输出文件**」——精灵既是渲染的输出、也是游戏的输入
2. 体积可控：精灵约 17 MB，仍小于已入库的 42 MB `.blend` / `.glb` 源素材
3. "产物可重建所以不入库"在此不成立——重建需装 Blender 并配好环境，成本不低，前端不应为此被阻塞

`out/`（占位）与 `dl/`（下载的原始压缩包）仍然忽略，前者可由 `gen.py` 秒级重建，后者已解压进 `models/`。

### 最终打包时须按 `assets.json` 过滤 `models/`

仓库保留整个素材包是有意的——换模型时要能挑，重新下载有成本。但**交付包与仓库不是一回事**：

```
assets.json 引用的模型:  约 30 个
models/ 下模型文件总数: 103 个
```

未被引用的那七十多个**不是交付要求所说的「输入文件」**，它们连渲染都没参与。
同一份清单还专门要求「删除 Debug/Release 中的编译文件」，可见是希望交付包精简的。
打包脚本应当读 `assets.json`，只带被引用到的模型。
