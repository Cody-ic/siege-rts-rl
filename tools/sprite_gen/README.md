# 精灵生成

两条产图路线，产物格式相同（`<标识符>_<状态>_<朝向>[_<帧号>].png`），前端代码不因换图而改动。

| 路线 | 脚本 | 用途 |
|---|---|---|
| **程序化占位** | `gen.py` | 第 1 周立刻可用，不依赖任何素材。尺寸与投影角必然一致 |
| **场景预览** | `preview_map.py` | 拼一张等距场景，兼作前端贴图与深度排序的参考实现 |
| **真实素材** | `blender_render.py` + `postprocess.py` | 正式画面。CC0 模型经统一相机与灯光预渲染成等距精灵 |

## 路线一：程序化占位

```bash
python gen.py out
```

输出 `out/<标识符>_<朝向>.png` 与 `out/_contact_sheet.png`。无依赖（仅 Pillow），
用于在美术就位前解锁前端开发。

## 路线二：真实素材

### 1. 只用 CC0 素材

**这是硬性要求，不是偏好。** 交付清单要求提交「软件源代码，包括输入文件」，
素材需随仓库提交。CC0 允许无条件复制、修改、再分发；其他"免费"许可通常不允许。

已核实可用的来源：

| 来源 | 许可 | 覆盖 |
|---|---|---|
| [Quaternius](https://quaternius.com/) | CC0 | knight、monsters、Animated Animal Pack（含 **Horse**）、Fantasy Props |
| [KayKit](https://kaylousberg.itch.io/) | CC0 | **Skeletons**、Adventurers、**Medieval Builder**、Dungeon |
| [Kenney](https://kenney.nl) | CC0 | 地形、瓦片、建筑 |
| [Poly Pizza](https://poly.pizza/) | **混杂** | 聚合站，含大量 CC-BY 的 Google Poly 存档，**须逐个查看许可标签** |

**不要使用 [Reiner's Tilesets](https://www.reinerstilesets.de/graphics/lizenz/)**：
其许可禁止将原始素材（含修改版）上传到自己的页面，与本项目"素材入库并随源码交付"冲突。

### 素材包本身的坑（下次换素材大概率还会撞上）

| 症状 | 原因 | 应对 |
|---|---|---|
| 模型整体渲成**品红** | `.blend` 把纹理路径写成与自身同级，分发时纹理却在单独的 `Textures/` 目录 | `relocate_missing_textures()` 按文件名逐级向上搜索并改写 `filepath`。Blender 的 `file.find_missing_files` 算子在无头模式下不可靠 |
| 渲出**空图** | 网格被作者设了 `hide_render=True`（Quaternius 的 Skeleton 即如此） | `normalize()` 中强制 `hide_render = hide_viewport = False` |
| 模型停在**默认姿态**（鹰只剩两片下垂的翅膀） | `libraries.load` 会载入动作数据块，但不会绑到骨架 | `set_action()` 显式指定；动作名各包不同（`Idle` / `Skeleton_Idle` / `Bat_Flying`），找不到时会打印可用列表 |
| 跨包组合比例失调 | 各包尺度互不相干（马高 6.91、骷髅高 5.09，原始单位无可比性） | `parts` 的 `scale` 先对齐比例，再用 `offset` 定位 |
| 拼装时**某个部件静默停在默认姿态** | 多包动作重名（马与盗贼都有 `Idle`），后载入的被 Blender 改成 `Idle.001`；按全局名查找会把马的动作绑到骑手骨架上，骨骼名对不上则**不报错** | `set_action()` 的候选限定在该部件刚载入的动作里 |
| 染色调到能看出阵营时，模型**糊成一块平色** | 线性混合按比例抹掉纹理明暗 | 默认改用 `COLOR` 混合：只换色相饱和度、明度照抄原图 |
| 想要冷色却染出**暗红** | `MULTIPLY` 只能压暗，加不出原图没有的颜色（棕马乘幽紫 = 暗红） | 幽灵战马那类须两步：`COLOR` 换色相 + `brightness` 压暗 |
| 染色与提亮**双双无效**，模型始终一团黑 | 该模型的本色明度极低（鹰的翅膀只有 0.04），`COLOR` 照抄明度就还是黑的；而 `brightness>1` 走混色节点时被颜色输入钳制到 1，等于没乘 | 这类模型改用 `tint_mode: "MIX"` 直接换色；提亮已改走不钳制的向量缩放节点 |
| 武器待机帧在手上、**一跑就脱手** | 按世界坐标摆放的绑定是静态的，手臂一动它留在原地 | `attach` 建立真正的骨骼父子关系 |

另外两个已知坑：Quaternius 的 **FBX 动画会损坏**，请用 `.blend` 或 glTF；
KayKit 的 **Legacy 版本**风格陈旧，须取重做后的新版。

### 2. 放置模型并登记

模型放在 `models/<素材包>/`（**保留素材包原目录结构**，否则 `.blend` 引用的纹理会失效），
然后在 `assets.json` 中登记。各家模型的朝向、尺度、原点、动作名都不一致，
这些差异**全部在 JSON 里用数据抹平**，不改脚本。

登记项：`cn` 中文名、`yaw` 朝向校正、`height` / `max_width` 尺寸、`lift` 抬升（空中单位）、
`action` / `frames` 动作与帧、`tint` / `tint_mode` / `brightness` 阵营染色。字段含义见
`assets.json` 顶部的 `_comment`。

**模块化素材用 `parts` 拼装**：Kenney 城堡包的塔身分为底座/中段/顶层/屋顶数块，
每块都从 z=0 起建模，单独渲染只是塔的一截。`parts` 按累计高度自下而上堆叠，
`gap` 可微调各段间距（旗帜等装饰件常需负值下沉）。

`parts` 同样用于**跨素材包组合**：鬼域骑士团 = 幽灵战马 + 骷髅骑手 + 压平的骑枪。
此时用 `scale` 对齐比例、`offset` 显式定位（设了 offset 即不参与堆叠）、`rot` 调整
握持角度（武器模型原点都在握把处，绕原点旋转正好等于改变持握姿态）。

### 骑乘：`pose` 与 `attach`

素材包里**没有骑乘动作**，直接把骑手放上马背，双腿会整根插进马腹。`pose` 在动作之上
叠加手工骨骼角度，把大腿前摆外张、小腿回折，绕开马身：

```json
"pose": { "L.UpperLeg": [70, 0, 35], "L.DownLeg": [-60, 0, 0] }
```

绕**局部 X 轴是前后摆动**，局部 Y 是骨骼自身轴向、转了没有任何效果（骨骼的局部 Y
就是骨长方向）。角度靠单独渲一次骨架标定即可，不必凭空猜。

`pose` 会**先在该帧求值再清除动作**——动作每次换帧都会重写骨骼变换，不清除的话手工
角度会被动画系统悄悄冲掉。副作用是该部件从此定格，所以马能跑而骑手保持坐姿。

武器用 `attach` 绑到骨骼上，不要按世界坐标估位置：

```json
{ "model": ".../Warrior_Sword.blend", "attach": "R.DownLeg.001", "rot": [-90, 0, 0] }
```

`attach` 建立的是**真正的骨骼父子关系**，不是算一次世界矩阵摆上去。这个区别只在
动画里才暴露：摆放式绑定在定格的部件上看着没问题，但骷髅一跑起来手臂摆动，
静止摆放的剑就留在原地脱手了——而**单看待机帧完全正常**。

原点是**骨尾**（即手部），局部 Y 沿骨长，所以手持武器的 `offset` 通常就是 0。
清单里的 `scale` 是世界尺度，代码会除掉从骨架继承的那一份缩放，与非绑定部件同义。

调握持角时注意：**等距视角下指向镜头的武器会被压缩成一条细缝**，看着像"尺寸变小了"。
判断尺寸对不对要看待机帧，不要拿奔跑帧下结论。

两个已知的命名坑：Quaternius 的**骷髅没有手臂骨骼**——它把手臂也命名成了
`*.UpperLeg.001`（肩高 z=3.23，从名字完全看不出来）；q_rpg 的人形角色则带一根
现成的 `Weapon.R`，武器直接绑上去即可。

### 动画状态

每个实体用 `states` 声明若干状态，当前是 `idle` 与 `move`：

```json
"states": {
  "idle": { "action": "Idle_Weapon", "frames": [1] },
  "move": { "action": "Run_Weapon",  "frames": [1, 6, 11, 16] }
}
```

动作挂在 `parts` 里的实体（骷髅、骑兵）改用 `parts` 覆写，键是部件下标：

```json
"move": { "frames": [1,6,11,16], "parts": { "0": { "action": "Run" } } }
```

未声明 `states` 的实体（建筑、攻城锤）视为只有一个 `idle` 状态，前端因此可以
对所有实体一视同仁地按 (标识符, 状态) 取图。

带武器的角色要用 `*_Weapon` / `*_Holding` 动作变体（`Run_Weapon`、`Run_Holding`），
否则奔跑时武器会脱手——这类模型的武器是**模型自带**的，与 `attach` 无关。

**画布按全部帧的并集确定**，否则奔跑循环里前后腿全展的那几帧会被悄悄裁掉。

注意 `libraries.load` 只拉 `objects` 时，**仅有当前绑在对象上的动作会跟着进来**
（马的 `Run` 就因此缺失），所以要显式载入 `actions`。

### 阵营配色

**染色的职责是让玩家一眼分清敌我**，不是美化。守方戍卫弓手与攻方亡灵弓手曾共用同一个
模型、只靠染色区分——这在剪影上完全读不出阵营，属于机制可读性缺陷（见 CLAUDE.md
「风味名不得遮蔽机制可读性」）。现在攻方一律为骷髅形体 + 幽蓝/幽紫冷色，守方为
有血肉的人形 + 自然暖色；同为骑兵的逐风猎骑与鬼域骑士团靠**活马 vs 幽灵马**区分。

三个模式各有其不可替代之处，选错了只能靠加大强度硬凑，结果是把模型抹平：

| 模式 | 行为 | 用在哪 |
|---|---|---|
| `COLOR`（默认） | 取染色的色相饱和度，**保留原纹理明度** | 绝大多数情况。要"更明显"应加大饱和度，而非强度 |
| `MULTIPLY` | 只能压暗，**加不出原图没有的颜色** | 压暗金属、木料 |
| `MIX` | 线性混到平色，会抹掉明暗层次 | 基本不用 |

`brightness` 补上 `COLOR` 做不到的明暗调整：幽灵战马是「换色相 + 压暗 0.55」，
空中单位则要**提亮**（蝙蝠贴图本身很暗，不提亮在地表上根本看不见）。

### 3. 渲染

```bash
blender --background --python blender_render.py -- --manifest assets.json --out out_3d
blender --background --python blender_render.py -- --only Knight,Phoenix   # 只渲部分
python postprocess.py out_3d
```

## 尺寸约定：一律以**格子边长**为 1

`TILE_SIDE = 1/√2 ≈ 0.707` 世界单位。约定是「1 世界单位 = `px_per_tile` 像素
（沿屏幕横轴）」，而边长 s 的正方形投影后横跨 √2·s，故 s 取 1/√2 才能让菱形正好是
`px_per_tile × px_per_tile/2` 像素。**改这个数等于改掉整套素材。**

`height` / `max_width` / `lift` 都以**格边长**为 1，`max_width = 1.0` 正好占满一格。
早先误以菱形的**屏幕宽度**为 1，等于把所有实体放大了 √2 倍——单位比地砖还大、
大树比战马还矮。这类比例错误在单看一张图时完全看不出来，**必须把不同类实体
按锚点对齐排在一起才会暴露**。

### 三种定标方式

| 方式 | 行为 | 用在哪 |
|---|---|---|
| `modules: k` | 1 个模型单位 = k 格边长，**不做归一化** | Kenney 全套 |
| `kind: "tile"` | 按水平 footprint 定标到一格 | 地砖 |
| `height`（默认） | 按高度定标，`max_width` 约束水平尺寸 | Quaternius 角色 |

**Kenney 整套件都建在 1.0 模数上且内部自洽**（墙高 1.31、塔身 1.01、大树 1.85、
攻城锤长 2.09、地砖 1.00），所以统一乘一个系数即可让全套件与格子、以及彼此之间的
比例自动正确。**逐个手调高度反而会破坏这份自洽**——这是上一版比例失控的直接原因。

Quaternius 的角色原始尺度毫无可比性（马高 6.91、骷髅 5.09），只能按高度归一化。
步兵定为 0.9 格边长，骑兵 1.2。

## 地形三类：地面 / 障碍物 / 资源点

`kind: "tile"` 的条目是地砖：画布不留白、菱形正好占满，后处理跳过描边与投影
（地砖本身就是地面，描边会让整片地面变成一张黑格子网）。

- **可通行地面** —— 草地 / 草地·二 / 土地 / 道路 / 焦土，共用 `ground.glb`
  （只有 4 个顶点的 1×1 平面四边形，无厚度），靠染色区分
- **障碍物** —— 巨石（阻断通行与视野，制造隘口）、密林（藏兵位）、水域 + 桥。
  这三类不是装饰：CLAUDE.md 的「骑兵冲锋助跑距离」「集结区方向选择」
  「视野遮挡是侦查的物理基础」「flow field 寻路」四条都以它们为前提
- **资源点上的建筑** —— 采石场 / 伐木场 / 金矿场。**必须与作为景物的树和碎石可区分**：
  它们是攻方的打击目标，玩家找不到自己的资源点，就判断不出攻方在打哪一种

试过用 `ground-hills.glb` 做起伏地砖，**失败**：0.29 的隆起在等距视角下读作草地上的
绿疙瘩而不是地面起伏，反而破坏了地面的连续感。改用同色微差的第二种草地供交错铺设。

**平面地砖的染色要额外压暗。** 朝上的漫反射面在三点光下会被打得很亮，
水域按 `MIX` 混到饱和蓝仍会渲成灰蓝，须配 `brightness ≈ 0.5` 才读得出是水。

## 场景预览：前端契约的可执行示例

```bash
python preview_map.py out_3d
```

`preview_map.py` 读 `_sprite_meta.json` 拼出一张 8×8 的等距场景。它既是渲染结果的
目视校验，也是**写前端时该照着抄的四十行**：

- `grid_to_screen()` —— 等距的全部数学就两行
- `place()` —— 把**锚点**对齐到格心，而不是把图片左上角对齐到格心。
  各精灵画布尺寸不同，按左上角贴会让高个子单位整体上浮
- 主循环 —— 画家算法按 `gi+gj` 从小到大画。地面与其上的物件遵循同一个顺序，
  混排也不会穿插错

已知性质：地砖边缘的抗锯齿会让相邻格之间留下一条极淡的缝，看起来像一层网格。
本项目地图本就是 grid，暂按可接受处理；若要消除，前端把地砖放大 1~2 像素绘制即可。

## 为什么混用不同来源不会翻车

混用 **2D** 等距精灵几乎必然翻车——投影角、比例、光照方向已经烤死在像素里，无法统一。

混用 **3D** 模型则可以救：所有模型都经过**同一个正交相机 + 同一套三点灯光 + 同一分辨率**，
再统一缩放到规定高度。风格差异在渲染阶段就被压平了。这正是选择预渲染路线的原因。

## 关键约定

- **相机俯角 30°**（绕 X 60°、绕 Z 45°），投影瓦片为 **2:1**。改这个值等于改掉整套素材。
- **旋转模型而非旋转相机。** 相机与灯光固定，各朝向受光不同，符合等距游戏观感；旋转相机会让模型受光恒定，画面发平。
- **描边与地面投影在后处理做，不在 Blender 做。** 描边保证暗色单位在暗色地表上剪影可读；地面投影同时承担"表达高度"的职责——空中单位投影留在地面、本体抬高，玩家一眼看出它在飞。

## 前端契约：`_sprite_meta.json`

随精灵输出，**这是前端唯一应当依赖的尺寸约定**：

```json
{
  "px_per_tile": 256,
  "sprites": {
    "Spear": { "cn": "铁壁枪卫", "states": {
      "idle": { "canvas": [302, 406], "ground_anchor": [151.0, 297.4], "frames": [1] },
      "move": { "canvas": [374, 466], "ground_anchor": [187.0, 337.6], "frames": [1,6,11,16] }
    }},
    "Wall": { "cn": "城墙", "states": {
      "idle": { "canvas": [332, 456], "ground_anchor": [166.0, 344.5], "frames": [1] }
    }}
  }
}
```

文件名是 `<标识符>_<状态>_<朝向>[_<帧号>].png`，**单帧时无帧号后缀**。
建筑等静态实体也有 `idle` 状态，前端因此不必对它们特殊处理。

`canvas` 与 `ground_anchor` **按 (标识符, 状态) 读取**：不同状态的画布大小不同
（奔跑时四肢伸展更占地方），但锚点始终对齐同一个地面点，所以 idle↔move
切换时精灵不会跳动。

**画布尺寸逐个实体适配，因此 `canvas` 与 `ground_anchor` 必须按精灵读取。**

实体高度跨度约 5 倍（幽影窥使 0.45 瓦片 ~ 领主堡垒 2.15 瓦片）。统一画布只能二选一：
要么裁掉高的，要么把矮的挤成一小点。因此本流水线**固定世界→像素缩放**（`px_per_tile`），
只让画布随实体变化——相对大小因此始终正确，单位本就应当显得比塔矮。

画布由 `frame_for()` **把归一化后的几何投影到相机平面实测**得出，不按声明尺寸估算。
早先按 `height` / `max_width` 估算有两个错处，都只会静默地裁掉画面而不报错：

- 等距投影下**水平位移也会产生纵向的屏幕位移**。骑兵又长又矮，纵向占位远大于其
  `height`，按高度定画布会裁掉马蹄
- `max_width` 是归一化的**上限**而非实际宽度，步兵的画布因此宽了近一倍

底部另留出投影余量（`SHADOW_PAD`），否则宽实体的地面投影会被下边缘切掉半个。

`ground_anchor` 是画布内**代表实体脚底的像素坐标**，前端据此把精灵对齐到格子中心。

- 由**相机投影精确算出**（世界原点的投影位置），不是估算
- **不要靠 alpha 包围盒底边推算**——实体带披风、长矛、尾羽、旗帜时会明显偏移
- 后处理画地面投影也用它。空中单位抬升后，本体与投影的间距即"飞行高度"

`--only` 部分重渲时元数据会与已有条目**合并**，不会丢掉其余精灵。

## 后处理是幂等的

`postprocess.py` 默认原地覆盖输入目录。为避免重复运行不断叠加描边与投影（且**不报错**，只是一次比一次糟），处理过的 PNG 会写入文本标记 `siege_postprocessed`，再次运行时自动跳过。

`--force` 可强制重处理，但**只应对未经后处理的原始渲染输出使用**。

## 精灵成品入库

`out_3d/` 的 300 张精灵（11 单位 + 11 建筑 + 13 地形）、`_sprite_meta.json` 与
场景预览图 **入库**，理由三条：

1. 交付清单要求「软件源代码**包括输入文件和输出文件**」——精灵既是渲染的输出、也是游戏的输入
2. 体积可控：精灵约 13 MB，仍小于已入库的 42 MB `.blend` / `.glb` 源素材
3. "产物可重建所以不入库"在此不成立——重建需装 Blender 并配好环境，成本不低，前端不应为此被阻塞

`out/`（占位）与 `dl/`（下载的原始压缩包）仍然忽略，前者可由 `gen.py` 秒级重建，后者已解压进 `models/`。

### 最终打包时须按 `assets.json` 过滤 `models/`

仓库保留整个素材包是有意的——换模型时要能挑，重新下载有成本。但**交付包与仓库不是一回事**：

```
assets.json 引用的模型:  约 30 个
models/ 下模型文件总数: 103 个
```

未被引用的那七十多个**不是交付要求所说的「输入文件」**，它们连渲染都没参与。
同一份清单还专门要求「删除 Debug/Release 中的编译文件」，可见是希望交付包精简的。
打包脚本应当读 `assets.json`，只带被引用到的模型。
