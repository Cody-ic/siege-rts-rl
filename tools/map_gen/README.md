# `tools/map_gen/`

地图文件的读写、校验与生成。`地图与场景设计.md` 第 6、8、9 节的可执行部分。

> **规范在 `地图与场景设计.md`，本文只讲工具怎么用、以及实现上做了哪些不在
> 规范里的决定。** 两处写同一件事必然漂移 —— 仓库已经为此开过三次订正 PR。

## 现在有什么

第 8 节的条目里，第 20 条已移出本表（落到生成器的批量报告，见
`地图与场景设计.md` 8.1），其余的实现状态见下面的进度表——**具体几条已实现
不写在这里**，理由与「用法」那节的同一条纪律相同，`--list` 会自己报。
生成器（第 9 节）已落地，见 `generate.py`。

| 文件 | 是什么 |
|---|---|
| `mapfile.py` | 地图读写与 `content_hash`。**全仓库唯一的地图 I/O 入口** |
| `grid.py` | 格子层解码、三张标志位、连通性原语、城区推导 |
| `validate.py` | 第 8 节校验器，以及条目状态注册表 |
| `selftest.py` | 自检，注册为 ctest `map_gen_self_test` |

## 用法

```bash
py tools/map_gen/validate.py --list           # 列全部条目的状态，不读地图
py tools/map_gen/validate.py maps/            # 校验目录下所有地图
py tools/map_gen/selftest.py                  # 自检（条目数不写死，见下）
ctest --test-dir build -C Release -R map_gen  # 走 ctest
```

**条目数刻意不写在这里**——`--list` 与 `selftest.py` 跑完都会自己报，写死的数字
每加一条检查就要改一处，忘了改就是又一次「同一件事写在两处」（CLAUDE.md 那条
纪律），本文件自己在下面「进度表」那句已经因此改过一次。

**「阻塞」与「待阈值」的条目会照常出现在报告里**，不静默跳过。跳过若不可见，
校验器会随着条目增加慢慢变成一个只查几条的东西，而每次跑都是绿的 ——
正是 #24 那一整轮「该红却绿」的形态。

**用 `py` 而不是 `python`。** Windows 上 `python` 往往是 Microsoft Store 的
空存根，跑起来只会弹商店页面。CMake 侧走的是 `find_package(Python3)` 找到的
解释器，不受这个影响。

代码里 `import mapfile` 靠的是 `sys.path[0]`（脚本所在目录），所以从任何工作
目录调用都成立，不需要设 `PYTHONPATH`。

## 三个实现上的决定（规范没写，但绕不开）

### 1. 坐标是 `[x, y]`，而 `rows[y][x]`

6.2 的字段说明没有明写坐标顺序。示例里四个集结点分别落在上 / 右 / 下 / 左边缘
（`[48,2]` `[94,48]` `[48,94]` `[2,48]`），只有按 `[x, y]` 读才讲得通。

弄反了在方形地图上**不会立刻报错**（只是整张图转置），所以自检用一张
7×5 的非方形图钉住它。

### 2. `content_hash` 取的是「规范序列化」而非「规范化文本」

6.3 说规范化 = LF + 去尾随空白。本工具做得更强：**删掉 `content_hash` 键之后
重新按固定方式序列化，再对结果取 SHA-256。**

因为文本级规范化解决不了另外三种同样会改变字节、症状却一模一样的差异：

| 差异 | 举例 |
|---|---|
| 缩进宽度 | 有人用编辑器顺手格式化了一下 |
| 键的顺序 | 不同 json 库 / 版本的序列化顺序 |
| 非 ASCII 转义 | `"王国边境"` vs `"王国..."` |

规范序列化把三种一次全消掉，LF 与无尾随空白只是它的副产品。
**建议 6.3 相应改写**，未改之前以本工具为准 —— 它是可执行的那一份。

### 3. 斜向不穿角，取最严的一种

`CLAUDE.md` 把动作定为「8 方向移动 + 停止」，所以连通性按 8 邻接算。
但**斜向能否穿角文档没有定义**（属 `rts_core` 移动模型，接口未定稿），
这里取「两个正交邻格都可通行才让过」。

**归口现在有了**：`rts/action.hpp` 的 `kDiagonalNeedsBothOrthogonal = true`，
取值与这里一致，所以行为不用改；改的只是「这条假设存放在哪里」。

**但「保守 = 安全」不是一条全局性质**，它取决于该条检查的极性：

| 检查形态 | 例 | 少给通路的后果 |
|---|---|---|
| 必须连通 | 第 4、11、12 条 | 多报（安全） |
| 必须存在一条通路 | 第 8 条 | 多报（仍安全） |
| **不得存在一条通路** | **第 10 条** | **漏报（不安全）** |

第 10 条真的漏报过：它按「是不是森林」flood，而**穿角也用了同一个谓词**，
于是一条**斜向**森林链走得过去、检查却报通过（单位斜走时要求的是那两个角格
可通行，它们完全可以是 `Plain`）。`neighbors()` 因此把 `passable` 与 `corner`
分成两个谓词。**新增检查时先问它的极性，别默认「保守就安全」。**

### 第 12 条按「归因」判定，不只是「不通」

先算正常通行下从 `keep` 出发的可达集，再算把 `Water` 也当可通行时的可达集。
**只在后者通、前者不通时**才判定是水切断的。

不这么做的话，被 `Rock` 封死的通路会同时报到第 4 和第 12 条上，
而第 12 条要说的是「这条通路缺一座桥」，与「这里根本不该封死」是两种不同的修法。

### 城区推不出来 —— 它挡住第 9 条，**但挡不住第 8 条**

6.2 写「初始缺口不显式存储 —— 缺口就是城圈上没有墙段的位置，由校验器推导」。
这句话预设「城圈」是已知的，但地图文件里没有这个东西，而 `initial_walls`
本身带缺口（第 8 条要求如此），墙段集合不闭合，反推不出闭合轮廓。

flood-fill 两种障碍取法都不成立：

- 障碍取 `Rock ∪ Water` → 缺口/城门本来就是 `Plain`，从缺口处漏到城外（2026-08-31 前这条写「走廊口」，指旧设计）
- 障碍再加上墙 → 第 8 条强制留缺口，缺口处照样漏

**这不是选错了障碍集，是问题本身：一条不闭合的曲线不把平面分成内外两部分。**
任何 flood-fill 变体都绕不过去，除非引入「能填多大缺口」这类形态学参数，
而那又是一个待标定的数值 —— 用数值旋钮去定义结构约束，方向就错了。

更尖锐的形式：**`derive_city_area()` 当且仅当在第 8 条该判失败的地图上推导成功**
（闭合环 → 成功；留缺口 → 抛 `CityAreaUndecidable`）。不是「有时候漏」。

所以城区必须由地图**显式**给出。这顺带给 #26 的 A4 多一条论据：候选乙的城区
mask 不只是封住「设防」那个洞，它还是第 9 条能够实现的前提。

在城区来源定案前，`grid.derive_city_area()` 只在城圈完整时可用，
**泄漏即抛 `CityAreaUndecidable`，不返回一个看起来像样的错答案。**

#### 但第 8 条不需要城区 —— 判据换掉即可

第 8 节那张表写的目的是「『AI 利用已有缺口』指标第 1 波测不了（2.3）」。
那个性质可以**直接问**，不必绕道城圈：

> 存在一条从任一集结点到 `keep`、全程不穿过任何墙段的通路。

原语现成，就是 `grid.blocked_by_walls_too`。而且它**比字面判据更贴合意图**：
一个缺口若被第二道墙堵在后面，字面判据（城圈上有一格没墙）会放行，
而这条判它没缺口 —— 那才是对的，AI 确实进不来。`Gate` 算墙、要打才过，
也自动落在正确一侧。三种形态都有用例钉住。

### 第 14 条的度量取切比雪夫，而且这个选择与视野形状无关

`rts/fog.hpp` 明写视野解算的形状还没定（圆？方？分兵种半径？），
但第 14 条不必等它：半径 R 的**方形**视野覆盖 `cheb ≤ R`、**圆形**覆盖
`euc ≤ R`，而 `cheb ≤ euc` 恒成立 ⇒ **方形球包含同半径的圆形球**。
所以 `cheb > R` 对两种形状都够，且它是所有满足此性质的度量里最弱的一条。

欧氏为什么危险：`dx = dy = R` 时 `cheb = R`（方形视野**看得见**），
而 `euc = R√2 > R`（欧氏判据**放行**）—— 那正是第 14 条要防的那件事。
曼哈顿与 BFS 步数都 ≥ 切比雪夫，同样危险。

**刻意不做成 `vision_metric` 那样的配置旋钮**：留一个旋钮意味着有人某天会把它
拨到欧氏，而**拨错的症状是「校验通过」**。也**不建模遮挡** —— 忽略遮挡等于
高估覆盖，落在安全那一侧。实现与论证在 `grid.chebyshev`，用例钉住那条不等式。

## 加新字段时记得

`.gitattributes` 已用 `*.json text eol=lf` 覆盖地图文件，所以加 JSON 字段
不需要动它。但 `#21` 留下的规矩是：**新增会被程序读取或参与哈希的文本格式时，
要同时在 `.gitattributes` 里登记**。若将来引入 `.toml` / `.csv` 产物，别忘了。

`mapfile.KNOWN_LAYERS` 是白名单，`layers` 里出现未登记的层会**直接报错**而不是
忽略 —— `no_bulid` 这类拼写错误若被静默忽略，那一层就相当于全 0，
而地图看起来完全正常。新字段进契约时要同步更新它与 `check_format`。
