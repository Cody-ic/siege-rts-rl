# `tools/balance/`

数值设计与平衡工具（纯 Python，无 C++ 依赖）。

`CLAUDE.md`「平衡工具：成本产出矩阵」要求每格记录 1v1 对抗的期望资源盈亏，
作为调数值的依据与答辩材料。这个目录是它的**最小可行实现**——不是最终方案。

## 文件

- `combat_math.py`：逐字复现 `rts_core/include/rts/combat_math.hpp` 与
  `rts_core/src/mechanics.cpp` 里的战斗公式（`apply_permille` /
  `level_permille` / `charge_permille` / `anti_charge_permille`），
  用于在没有 `bindings/`/`train/` 的情况下快速验证数值改动。
  **改引擎侧公式后，这里要同步改**，否则两边会漂移。
- `cost_output_matrix.py`：读 `game/data/stats_placeholder.json`，对
  `CLAUDE.md`「克制二部图」里点名的每一对关系跑闭式 1v1 交换比。
- `balance_solver.py`：守方的**联立约束优化**与配平参数反解。需求 `D(w, L_d, A)`
  对塔数二分实测（调 `siege_race.fight_entry`，不复制战斗）；供给**石材按存量、
  金币按流量**（实测塔零损失、弓手每波全灭）；堡垒等级 `K` 同时买建筑等级上限、
  人口上限、兵种等级上限，三者抢同一份石材。三种模式：
  `upgrade`（升级划不划算）/ `margin`（余量曲线 M(w)）/ `scan`（参数扫描）。
  **结论与那条不可能性命题在 `攻守配平的数学模型.md`。**
- `economy_race.py`：把**地图上的资源点分布**接进 `siege_race` 的经济那一半
  （读 `game/data/maps/pool/` 的池图，逐簇解禁 + `tier` 产出倍率 + 采集建筑的
  造价工时 + 工匠与人口上限）。**战斗一字不复制**，`fight_entry`/`fight_inside`/
  `roster` 全部从 `siege_race` import——只换经济，两份结论才可比。
  结论在 `资源点分布与经济平衡.md`；`tier_income_permille` 是与数值表并列的
  **外生输入**，唯一真相在 `rts/world.hpp`，这里抄了一份占位值。
- `pop_cap.py`：守方**人口上限**的三条判据（2026-09-03，试玩反馈「2 级 12 太少了，
  比敌人还少」）。`波次预算曲线与堡垒等级曲线.md` §2.1 定 `8+2K` 时只用了
  「咬得住」一条，而那条**整个没有把攻方那条曲线放进来**；这里把它和
  **C2 不是天花板**（`cap × √B(等级上限)` 跟得上攻方 `Σ√B`）、
  **C3 够得着**（`K` 真的涨得起来）并排跑。
  **结论：`8+2K` 不是病根，`K` 不动才是**——升一级堡垒（200 石 + 200 木）买到的
  火力只有同样石材建塔的 1/1.8、血量的 1/3.8，所以「一局只升 1 次」是这个比价下的
  正确答案，于是 `cap(K)` 里的 `K` 在实战中是常数、公式的形状无关紧要。
  顺带查出第二个病（两侧的等级尺度不可比，第 8 波克制倍率只剩 21%）。
  详见 `波次预算曲线与堡垒等级曲线.md` **§2.2**。
- `budget_curves.py`：攻方兵力预算 / 编成位 / 名义等级、守方金币收入 / 解禁节奏 /
  战力存量的曲线模型。`波次预算曲线与堡垒等级曲线.md` 给了公式但只能被**读**，
  这个脚本把它们变成可跑的，并把其中**结构性**的四条做成会红的断言。

## `siege_race.py`：攻守实力的正确货币（2026-09-02）

`budget_curves.py` 把「单位 HP×DPS 之和」叫总战力，并写成 `总战力 ≡ 兵力预算`。
**那是量纲错**：等级各开一份平方根之后，一波兑现到场上的血池与火力都是 Σ√B、不是 ΣB
（现行曲线第 5 波兑现率 43%、第 20 波 32%）；而且攻城不是消耗战、是入口处的赛跑。
`siege_race.py` 按后者建模，四种模式分别复算 `攻守实力模型与平衡分析.md` §2–§4 的表：

```bash
py tools/balance/siege_race.py pool      # 预算兑现率
py tools/balance/siege_race.py towers    # 拦住 Ram 要几座塔（含旧曲线对照）
py tools/balance/siege_race.py grid      # 多波单因素敏感性
py tools/balance/siege_race.py base      # 逐波轨迹
```

模型定义、结论、局限与「既有文档疑似误导清单」都在那份文档里，这里不复述。

**它的收入一侧是三个常数（各一座采集建筑），地图的资源点分布整个没进去**——
§3 那个「每门每波 0.85 座塔」就是「一座采石场 ÷ 80」。换成 12 张池图的
实际分布后是 3.7–13.2 座（内环带全铺）。检查与实验见 `economy_race.py` 与
`资源点分布与经济平衡.md`；**`siege_race.py` 本身没有为此改动**，它的表仍逐行可复算。

## §7 校准 runner 已落地（2026-09-02）

`攻守实力模型与平衡分析.md` §7 要的 runner 在 `tools/calibration_runner/`
（C++ 可执行文件，链接 game + rts_core，无渲染、无第三方依赖）：多种子跑
`DemoBattle` + `DefenderScript`，逐波记破口时刻、`Ram` 到墙血量与塔火、
塔 AOE 逐发命中数（rts_core 里的唯一埋点 `World::volley_hits()`）、
`Phoenix` 目标序列、门边 13 格墙弓手数、守方损失、堡垒血量与波长，输出
机器可读 JSON。用法与字段全表见该目录 README；首批数据的量级与「待封缺口」
的拟合结论见 `攻守实力模型与平衡分析.md` §7.1。本目录的 Python 模型脚本
（`siege_race.py` 等）是**闭式聚合模型**，runner 是**逐单位仿真**——两者
互为对照，后者是前者的校准来源。

## `budget_curves.py` 里三条结构结论

推导写在该文件头部，这里只留结论（同一件事写在两处必然漂移，所以不复制论证）：

1. **`cost(等级)` 的阶决定「多买一个 vs 升一级」是不是真决策。** 若某个
   指数下有一侧严格占优，宏观层那个决策塌到角上——而 `CLAUDE.md` 要它是真决策
   （「40 个低级杂兵铺开 / 8 个高级精英硬凿一点」）。**所以这是结构，不是数值。**
   **订正（2026-09-02，详见 攻守实力模型与平衡分析.md §8 第 1 条）**：原表述
   「必须与战力同阶」隐含 α=1（隘口/线性律）没写出来，被 §12 的等成本对拼
   推翻；定案取 `c ∝ √B(L)`（已落地 `World::train_cost_gold`），**有意**让
   「凿点用质、铺开用量」（`数值设计与成本产出矩阵.md` §12.5），「只堆精英」
   由人口上限 `8+2K` 与兵种等级上限 = 堡垒等级封顶。
2. ~~**`cost ∝ 战力` 一旦成立，「波次强度曲线」与「兵力预算曲线」是同一条。**~~
   **订正（2026-09-02，详见 攻守实力模型与平衡分析.md §8 第 1 条）**：
   **不成立。** 那条推导里的「总战力」是 ΣB（HP×DPS 之和），兑现到场上的是
   Σ√B（§2），兑现率随编成形状变——所以是**两条**曲线：兵力预算曲线之外
   还有一层兑现映射，正确货币下的模型是 `siege_race.py`。
3. **波间隔 × 收入率、出矿速率 × 矿点密度，在预算上都只有乘积进去。**
   所以它们各自不是两个自由度：波间隔该由 episode 长度与建造/训练耗时钉死，
   收入率再去解目标比值。**分布形态是另一回事**（它管「围哪一簇」那个决策）。

它还给出一条容易被漏掉的诊断：**收入不随波数增长时，守方战力存量有一个与波数
无关的天花板**（= 每波收入 ÷ (1 − retention)，几何级数）。于是调 retention 或
起始收入只是平移，**改斜率只能靠解禁节奏或压低兵力预算指数** ——
这正好对上 `CLAUDE.md` 那句「主要的难度旋钮是解禁节奏与强度曲线之比」。

## 用法

```bash
py tools/balance/cost_output_matrix.py              # 克制二部图逐条
py tools/balance/cost_output_matrix.py --scenarios  # 另加多场景对照
```

改了 `stats_placeholder.json` 里任何单位/建筑的数值后，先跑一遍这个脚本，
看有没有哪条克制关系被验证成"未通过"或"幅度薄"，再提交。

**`--scenarios` 存在的理由是防注释过期。** 那几个多场景的秒数此前只以数字的
形式活在文档与 JSON 注释里，而那些数不会随数值表更新——`Shade` 那条注释就是
这么过期的：它引的「15s → 约31s」是 `damage=11` 时量的，而表里早已是 14
（当前值 10.71s → 21.43s）。放进工具之后，数跟着表走。

## 判据分三档，不是「谁胜」

原判据是 `对方用时 > 自己用时`，**而 `CLAUDE.md` 明写要的是「期望资源盈亏
（而非谁胜）」，且克制的定义是「以显著更少的资源投入击败目标」**。一个严格
不等号表达不了「显著」：`Shade` 克 `Archer` 曾以 10.71s vs 11.25s（差 4.8%）
记成「通过」，而那个幅度下两个 `Archer` 就能翻盘。

现在是 通过 / **幅度薄** / 未通过 三档，照 `tools/map_gen/validate.py` 那条
纪律办（三种状态都出现在报告里，不静默跳过）。只有"方向反了"才非零退出——
「幅度薄」的阈值 `SIGNIFICANT_RATIO` 是占位值，拿一个占位阈值让别人的构建红，
就是把待定当已定。

## 它仍然不是「资源盈亏」，而缺的是一个字段

要算盈亏得知道双方各投入多少资源。守方那侧有 `cost_gold`；**攻方那侧的货币是
「编成位占用」，而那个字段整个仓库都不存在**——`rts/stats.hpp` 没有，数值表里
也没有。`combat_math.cost_of()` 正是为它留的位置，所以它至今没有调用方。

所以「成本产出矩阵」现在只有产出、没有成本。**这不是"以后优化"，是下一步的
前置条件**：编成位落地之前，它不可能真的是成本产出矩阵。
（`README.md` 曾把「编成位占用」列进已落地的数值清单，那是一处笔误，已订正。）

## 已知局限（不回避）

闭式 TTK 近似**不是**真实批量仿真：忽略了接敌时间、路径绕行、混战中的
目标切换、AOE 命中密集度随实际站位变化等因素。它只保证"克制方向对不对"
这个一阶结论，不保证具体数字精确。一旦 `bindings/`+`train/` 落地，
应该换成 `守方AI与协同演化.md` 第 8 节写的两步法：黑箱优化（CMA-ES/
贝叶斯优化）在矩阵上搜候选数值 → 协同演化在完整博弈均衡下验收。

`COUNTER_GRAPH` 里标 `False`（跳过数值验证）的几条不是没验证，是**这个
工具的模型验证不了**——风筝（靠射程+速度差）、免费仇恨窗口（靠射程差）、
位置性克制（Flak vs Phoenix）都需要移动/站位建模，不是纯 DPS 对拼能测的。
详见《数值设计与成本产出矩阵.md》第 8 节。

## 墙类升级候选（2026-09-19）

`python tools/balance/fortification_curve.py --max-level 100` 输出旧/新血量、每级增量、单次及累计费用；`--building Gate` / `Fence` 可切换建筑。默认读取当前数值表，整数开方与取整跟随 C++ `StatsTable`。这是公式核算，不是战斗模拟。分段定义与真机回归结果见 `docs/fortification-upgrades/README.md`。

`siege_race.bhp` 已接入同一墙类曲线；其余聚合战斗假设（包括历史攻击周期近似）仍有局限，不能据此声称新版长局配平已验证。
